AI 协同开发：切片式开发训练手册

前言：为什么你需要一套 AI 时代的新手开发方法

版本：v0.1 全章初稿

这本书写给谁

这本书写给没有系统软件开发基础，但希望借助 GPT、Claude Code、Codex、Cursor 等 AI 工具把产品做出来的新手。你可能有业务想法，能描述需求，也能判断页面像不像自己要的东西，但不一定懂前端、后端、数据库、接口和部署。

本书不追求把你培养成专业程序员，而是训练一种更现实的能力：把模糊想法拆成 AI 能稳定执行的小切片，并通过页面预览、施工任务单、验收清单和返工单，把开发过程控制住。

本书的核心路线

产品合同 → 页面预览 → 最小闭环 → 切片任务 → 施工单 → 验收 → 返工 → 复盘

这条路线的重点不是“慢”，而是“可控”。AI 写代码越来越快，但写得快不代表做得准。人仍然要负责目标、边界和验收。

为什么不能一上来做完整系统

很多人第一次用 AI 做项目，会这样问：

我要做一个 AI 员工系统，请帮我生成完整 PRD、架构设计、数据库设计、前端页面、后端接口和开发计划。

AI 很可能给你一大堆内容：员工画像、任务系统、长期记忆、工具权限、审批流、日志、复盘、知识库、多 agent 调度。它们看起来都合理，但问题是你很难判断第一步要做什么，也很难审查这些内容是否真正服务于你的目标。

新手最缺的通常不是更多文档，而是过程控制力。你需要知道什么时候让 AI 收敛，什么时候让 AI 展开，什么时候停止生成，什么时候进入验收。

本书主案例

本书贯穿一个主案例：AI 员工任务创建与审批小闭环。

完整想法是：

我想做一个 AI 员工系统，可以给它分配任务，它能自己执行，还能在高风险操作前请求审批。

但本书不会从完整系统开始，而会从最小任务闭环开始：

用户输入任务 → 系统生成任务草案 → 用户编辑/确认 → 任务进入列表。

后续再接审批、执行结果、复盘等切片。

你读完后应该能做到什么

  1. 把一句模糊需求压缩成一页纸产品合同；
  2. 识别系统里的最小闭环；
  3. 拆出第一个可开发、可验收的切片；
  4. 要求 GPT 先做页面预览，而不是直接展开后端；
  5. 给 Claude Code / Codex 写清楚施工任务单；
  6. 用验收清单检查 AI 产出；
  7. 判断问题属于产品返工还是实现返工；
  8. 写出可执行返工单；
  9. 通过复盘减少下一轮偏航；
  10. 建立自己的 AI 协同开发工作流。

本书最重要的底层判断

AI 时代，开发能力被重新拆分了。过去写代码是门槛，现在“定义问题、拆分切片、控制边界、验收结果”变成更关键的门槛。AI 可以帮你写代码，但它不能替你决定第一版应该解决什么问题，也不能替你承担“做出来是否有用”的判断责任。

所以本书反复强调一句话：

AI 负责生成，人负责判断；AI 负责执行，人负责验收；AI 可以扩展，人必须收敛。

如果你能记住这句话，后面每一章都会更容易理解。

第 1 章：为什么很多人用 AI 开发，最后做出来却不好用

版本：v0.1 全章初稿
本章定位：基础训练章节

本章你要学会什么

你要学会识别 AI 开发偏航的真实原因：不是所有失败都能归因于模型不行。很多时候，是需求边界不清、反馈太晚、文档过多、验收缺失导致结果不好用。

为什么这一章重要

AI 协同开发最容易失败的地方，往往不是模型不会写代码，而是人没有把目标、边界、检查点和验收方式定义清楚。本章的作用，是把一个容易凭感觉推进的环节，变成可以重复执行的训练动作。你不需要一开始掌握传统软件工程的全部知识，但你必须能把 AI 的输出限制在自己能审查、能判断、能返工的范围内。

核心概念

  • 文档幻觉：文档看起来完整，但不能指导第一步开发。
  • 需求偏航：实现方向偏离真实目标。
  • 实现偏航：方向对，但代码或细节没做到。
  • 反馈太晚：直到系统很复杂才发现问题。
  • 可判断检查点：每个阶段都留下能审查的材料。

核心观点

  1. AI 很容易把模糊需求扩展成看起来完整的系统。
  2. 新手无法审查过多架构文档，反而失去控制权。
  3. 做完了和能用了不是一回事。
  4. 需求问题和实现问题必须分开判断。
  5. 越早设置检查点，返工成本越低。

主案例推进

主案例中，用户说“我要做 AI 员工系统”。错误流程是让 GPT 直接生成 40 份完整文档，随后交给 coding agent 实现。结果页面很多，流程复杂，但第一条任务创建链路并不顺畅。正确推进方式是先问：最小可验证闭环是什么？

错误示范

我要做一个 AI 员工系统，请帮我生成完整 PRD、架构设计、数据库设计、前端设计、后端接口、开发任务拆解。

这个问法会导致文档爆炸、模型脑补、第一闭环缺失。你会得到很多看似专业的内容，但无法判断哪个该先做。

正确示范

我想做一个 AI 员工系统。请不要展开完整架构。
请先帮我判断：这个想法里最小可验证闭环是什么？
只输出 3 个候选闭环，并说明哪个最适合作为第一切片。

这个问法先要求 AI 收敛，而不是扩张。

方法拆解

1. 识别文档幻觉

判断一份文档是否有用，不看它多长，而看它能否支持你写出第一张施工任务单。

2. 区分需求偏航和实现偏航

如果目标、流程、文案或交互没定义清楚，是需求问题；如果定义清楚但代码没做到，是实现问题。

3. 提前反馈

不要等完整系统做完才看效果。先审产品合同，再审页面预览，再审施工单，再验收代码。

4. 控制审查带宽

新手无法同时审查完整架构、数据库、接口、前端和 agent 编排，所以必须压缩输出范围。

和 GPT 的对话演示

请审查下面的 AI 开发计划，判断是否存在文档爆炸、需求偏航、反馈太晚的问题。
请按“问题 → 风险 → 修改建议”输出，不要继续扩展方案。

补充案例：一个典型的新手失控链路

很多新手的失控不是突然发生的，而是一步一步发生的。

第一步，他说：“我想做一个系统。”
第二步，GPT 输出一份很完整的规划。
第三步，他觉得“既然 GPT 都写了，应该有道理”。
第四步，他把文档丢给 coding agent。
第五步，coding agent 生成了很多文件。
第六步，他打开页面，发现能运行，但不是自己想要的。
第七步，他开始说“帮我优化一下”。
第八步，AI 又改了很多东西。
第九步，项目越来越复杂，他越来越不敢动。

这个链路里，真正的错误不是某一步写错了，而是每一步都没有检查点。产品合同没有检查，页面预览没有检查，施工范围没有检查，验收标准没有检查，返工范围没有检查。

更细的偏航分类

1. 目标偏航

目标偏航是最早的偏航。例如你原本想验证“用户能不能创建 AI 任务”，结果 AI 开始帮你设计“AI 员工组织管理平台”。这时还没写代码，但方向已经偏了。

处理方法：回到一句话目标，问“第一版只完成哪一个动作仍然有价值？”

2. 范围偏航

范围偏航是功能越做越多。例如第一切片只做任务创建，但页面里出现员工配置、工具权限、审批流入口。

处理方法：拿本版不做项逐条对照，越界内容删除或移到后续切片。

3. 交互偏航

交互偏航是页面能用，但用户不知道怎么用。例如按钮文案含糊、空状态没有引导、点击后没有反馈。

处理方法：回到页面预览，补用户路径和状态设计。

4. 实现偏航

实现偏航是需求清楚但代码没做到。例如空输入不能提交已经写在验收清单里，但页面仍允许提交。

处理方法：写实现返工单，给复现步骤和期望结果。

v0.3 扩写：把“AI 开发偏航”讲透

这一章的核心，不是批评 AI，也不是让读者害怕使用 AI，而是帮助读者看见一个事实：AI 越强，越容易让新手误以为自己已经控制住了开发过程。

传统开发里，一个新手不会轻易要求团队一次性做出完整系统，因为他知道自己没有能力管理那么多模块。可在 AI 协同开发里，GPT 可以在几分钟内生成几十页文档，Claude Code / Codex 可以在一个仓库里快速改出大量文件，这会制造一种“项目正在高速推进”的错觉。

真正危险的地方在于：

  • 文档看起来完整，不代表边界清楚；
  • 代码生成得很快，不代表流程可用；
  • 页面做得很漂亮，不代表用户路径正确；
  • 模型能解释很多，不代表它理解了你的真实目标；
  • 你能让 AI 输出很多，不代表你能审查这些输出。

1.1 新手最常见的 5 种失控方式

失控方式一：把“想法”误认为“需求”

很多人的第一句话是：

我想做一个 AI 员工系统。

这句话只是一个想法，不是需求。想法通常方向感很强、细节很少、可解释空间很大。AI 最擅长填补空白。你只说“AI 员工”，它会自动想到员工画像、长期记忆、任务调度、工具权限、审计日志、工作台、审批流、复盘系统。每一个模块听起来都合理，但这些合理内容合在一起，就会变成新手无法审查的巨大工程。

更稳的做法是先把想法降级成一句业务动作：

我希望用户能输入一个任务，系统生成任务草案，用户确认后任务进入列表。

这句话还不是完整需求，但它已经比“AI 员工系统”更可控，因为它包含了用户、动作、结果。

失控方式二：把“完整文档”误认为“清晰文档”

AI 生成完整文档很容易。它可以给你 PRD、架构图、数据库表、接口清单、前端页面、后端服务、测试计划、部署方案。问题是，新手通常没有足够审查带宽。你看见 40 份文档，会觉得“很专业”，但很难逐条判断：哪些是当前必须做的？哪些是以后再做的？哪些是 AI 脑补出来的？哪些会增加实现难度？哪些会影响第一版验收？

因此，本书反复强调：开发早期不是文档越多越好，而是约束越清楚越好。

对于新手来说，第一阶段最有价值的文档不是大而全 PRD，而是：一页纸产品合同、第一切片定义、页面预览、施工任务单、验收清单。这五类材料能形成闭环。其他材料不是永远不要，而是不能太早展开。

失控方式三：把“能运行”误认为“能使用”

很多 AI 生成的项目都能启动，也有页面，也能点击，但用户真正使用时会发现：不知道第一步该点哪里；表单字段太多；按钮文案不清楚；任务提交后状态不明；出错时不知道原因；页面有很多当前不需要的功能。

这类问题不是代码不能运行，而是产品路径没有控制住。验收时不能只问“项目能不能跑起来”，还要问“用户能不能按预期完成这一条闭环”。

在主案例里，第一切片不是“AI 员工系统能不能运行”，而是：

用户能不能完成：输入任务 → 生成草案 → 编辑草案 → 确认创建 → 在列表看到待执行任务。

失控方式四：把“模型建议”误认为“产品决策”

GPT 经常会给出建议：增加员工配置、增加权限体系、增加风险等级、增加日志追踪、增加知识库、多角色协作。这些建议未必错，但它们不应该自动变成当前版本的开发范围。

新手要建立一个意识：AI 可以提出建议，但产品决策必须由人确认。

每次 AI 提出新增功能时，你都要问：

  1. 这个功能是否服务第一切片？
  2. 没有它，第一切片是否仍能验收？
  3. 加上它会不会增加不可控复杂度？
  4. 它是否应该进入待办池，而不是当前施工单？

如果答案是不确定，就先放入“后续待办”，不要进入当前切片。

失控方式五：把“返工”误认为“重新开始”

AI 开发中出现偏差很正常。真正拉开差距的不是是否会偏，而是偏了之后能不能收回来。很多新手发现页面不对，就会对 coding agent 说：

这个不对，重新做一下。

这句话会让 AI 再次发散。正确做法是基于验收项写返工单：

请只修复验收项 2 和验收项 4 未通过的问题。
不要新增页面，不要修改任务列表布局。
当前问题：空输入仍可提交；确认创建后列表没有显示“待执行”状态。
期望结果：空输入按钮禁用；确认创建后列表新增一条任务，状态为“待执行”。

返工不是情绪表达，而是一次有边界的小施工。

1.2 主案例：一次典型偏航全过程

假设你对 GPT 说：

我想做一个 AI 员工系统，能够给员工分配任务，员工自动执行，高风险操作要审批，请帮我完整设计。

GPT 可能会输出这样的目录：产品愿景、用户角色、AI 员工画像、任务系统、工具权限系统、审批系统、记忆系统、计划系统、执行器、日志审计、前端工作台、后端 API、数据库设计、部署方案、安全策略、商业化扩展。

这套目录看起来很完整，但第一轮就存在三个风险。

**风险一：主链路没有被提前验证。**你还没有验证用户到底是否愿意用这种方式创建任务、任务草案是否真的有帮助、任务列表如何承接状态、用户是否理解审批。如果这些没验证，先做记忆系统和工具权限，就是在不确定的地基上盖楼。

**风险二：新手审查负担瞬间过载。**专业团队可以分工审查架构、接口、安全、权限、数据库。但本书读者很多是单人开发者、产品型用户、副业尝试者。他们真正能审查的是页面是否符合想法、流程是否顺、文案是否清楚、验收项是否通过。

**风险三：coding agent 会沿着错误边界施工。**如果你把巨大文档丢给 Claude Code / Codex，它会尽力完成。问题是它不知道哪些是必须做，哪些是建议做，哪些是以后做。最后你发现页面跑起来了，但不知道哪些文件为什么改了，也不知道哪里出了问题。

这就是“文档偏航 → 施工偏航 → 验收困难 → 返工失控”的连锁反应。

错误问法 1：一次要完整系统

问题：范围过大；输出过多；AI 会自动补功能；没有第一切片；后续无法验收。

改写：

最后推荐最适合作为第一切片的闭环，并说明理由。

错误问法 2：直接让 AI 写代码

帮我把这个系统做出来，技术栈你看着办。

问题：产品边界不清；技术选择不可控；无法判断改动是否合理；后续返工困难。

改写：

请只实现第一切片的前端静态可交互版本：用户输入任务，点击生成草案，编辑草案，确认后任务进入列表。
使用 mock 数据，不接真实后端，不实现审批、权限、长期记忆和真实执行。
完成后列出变更文件、运行方式、已知问题，并逐条对照验收清单。

错误问法 3：模糊返工

问题：“不对”不可执行；“优化”没有边界；AI 可能重构无关代码；新问题可能更多。

改写：

请只修复任务创建页的 2 个问题，不要修改其他页面：
1. 当前草案确认按钮在页面底部，用户容易忽略。期望放到草案卡片右下角。
2. 当前空输入时仍可点击生成草案。期望输入为空时按钮禁用，并显示提示文案。
修复后请说明修改了哪些文件，以及验收项 1、2 是否通过。

1.6 读者常见卡点

卡点一：我怕切太小，做出来没有价值

切片小不等于价值小。一个好切片要验证关键路径，而不是堆功能。任务创建闭环虽然小，但它验证了用户是否能把任务交给 AI 员工，这是整个系统的入口。

卡点二：我担心不提前设计架构，后面会返工

早期一定会返工。问题不是是否返工，而是返工成本是否可控。对新手来说，过早设计大架构更容易返工，因为你还没验证用户路径。

卡点三：GPT 总是自动补很多内容怎么办

使用三句话约束：

请只围绕当前切片工作。
不要展开完整系统。
不确定的内容放入待确认项，不要自行决定。

1.7 本章扩写小结

AI 开发失败，常常不是因为模型不会写，而是因为人没有建立检查点。检查点越晚，偏航越大；检查点越早，返工越小。

从下一章开始，我们会把这种控制力具体化为“切片式开发”：不是把系统拆成一堆模块，而是拆成一段段能看、能跑、能验收的小闭环。

第 2 章：什么是切片式开发，为什么它比“大而全设计”更适合新手

本章你要学会什么

你要理解切片不是把大任务拆小，而是拆出一段能跑通的业务闭环。一个好切片必须能看、能跑、能验收。

为什么这一章重要

AI 协同开发最容易失败的地方，往往不是模型不会写代码，而是人没有把目标、边界、检查点和验收方式定义清楚。本章的作用，是把一个容易凭感觉推进的环节，变成可以重复执行的训练动作。你不需要一开始掌握传统软件工程的全部知识，但你必须能把 AI 的输出限制在自己能审查、能判断、能返工的范围内。

核心概念

  • 切片式开发：围绕可验证闭环推进。
  • 纵向切片：从用户动作切到可见结果。
  • 横向拆分：按前端、后端、数据库等层拆。
  • 最小闭环：最短但完整的业务链路。
  • 可预览、可运行、可验收。

核心观点

  1. 切片不是小任务，而是小闭环。
  2. 新手优先做纵向切片，不要横向铺满模块。
  3. 好切片必须有用户动作和可见结果。
  4. 切片越小，反馈越快，偏航越容易修。
  5. 切片式开发不是降低目标，而是降低失控风险。

主案例推进

AI 员工系统可拆为任务创建、审批、执行结果、员工配置等候选切片。第一切片优先选“任务创建 → 草案确认 → 进入列表”，因为它最靠近用户第一动作，最容易预览和验收。

第一周做所有页面，第二周做所有接口，第三周做数据库，第四周联调。

这属于横向拆分。每层都有进度，但没有一条用户链路能完整跑通。

正确示范

这是一条纵向切片，虽然小，但能验证核心入口。

方法拆解

1. 找用户动作

好切片通常从用户动作开始，例如输入任务、上传文件、选择商品。

2. 找可见终点

终点应该是用户看得见的结果，例如任务进入列表、客户清单生成。

3. 用 mock 降低复杂度

真实 AI、真实后端、真实数据源都可以先 mock，先验证流程。

4. 写不做项

不写不做项，AI 会默认可以扩展。

补充说明：为什么纵向切片更适合 AI 协同开发

在传统团队里，横向拆分之所以可行，是因为团队中有人能统一把控架构，有人负责接口约定，有人负责联调，有人负责测试。但新手和 AI 协同开发时，通常没有这么多角色。你一个人既要提需求，又要审页面，又要让 coding agent 改代码，还要验收结果。

这种情况下，横向拆分会把风险推迟到最后。前端做完时，你不知道后端能不能接；接口做完时，你不知道页面是否真的需要；数据库做完时，你不知道业务流程是否已经变了。

纵向切片的好处是，每一次都围绕用户价值走一小段。你不需要判断全系统，只需要判断这一段是否成立。

切片大小的判断标准

一个切片太大，通常有这些信号：

  • 描述里出现“完整”“全部”“所有”；
  • 需要同时接多个外部系统；
  • 需要复杂权限、长期记忆、任务队列、消息通知一起完成；
  • 验收项写不出来；
  • 页面预览超过 5 个核心页面；
  • 你解释给别人听需要超过 2 分钟。

一个切片太小，也可能有问题：

  • 只有一个按钮，没有结果；
  • 只有数据库表，没有用户动作；
  • 只有页面静态布局，没有状态变化；
  • 做完后无法判断业务是否成立。

好的第一切片通常介于两者之间：功能不多，但链路完整。

好的切片名称最好包含动作和结果：

  • 好：创建任务并进入列表；
  • 差：任务模块；
  • 好：生成候选客户并标记跟进；
  • 差：客户管理；
  • 好：上传试卷并生成错题清单；
  • 差：学习系统。

名称越具体，越不容易发散。

v0.3 扩写：切片不是拆任务，而是拆闭环

很多新手第一次听到“切片式开发”，会自然理解成“把大任务拆小”。这个理解只对了一半。真正重要的不是“小”，而是“闭环”。

一个任务可以很小，但不是好切片。例如：

先建数据库表。

这确实很小，但用户看不见，也无法单独验证业务价值。它只是一个横向技术任务。

一个切片也可以包含前端、状态、mock 数据、简单交互，看起来涉及多个层面，但只要它围绕一条用户路径形成闭环，它就是好切片。例如：

用户输入任务 → 系统生成草案 → 用户确认 → 任务进入列表。

它可能需要页面、按钮、状态、列表渲染，但用户能走完，产品能验收，后续能接真实后端。这就是纵向切片。

2.1 横向拆分为什么容易坑新手

传统技术拆分经常按层划分：前端页面、后端接口、数据库、权限、测试、部署。这种拆法对成熟团队很自然，因为团队里有人分别负责不同层，并且有架构师保证整体一致。但新手用 AI 协同开发时，按层拆分会遇到三个问题。

问题一：每一层都做了一点，但没有功能能用

如果第一周做完数据库，第二周做完接口，第三周做完页面，第四周才联调，你要等很久才知道需求有没有错。AI 开发的优势是反馈快。如果你用横向拆分把反馈推迟，就浪费了 AI 的最大优势。

问题二：你无法审查中间产物

数据库表是否设计合理？接口是否 RESTful？状态管理是否优雅？这些问题对新手不友好。你可能只能觉得“看起来专业”。但页面路径、按钮文案、列表状态、错误提示，你能审查。切片式开发就是优先制造你能审查的产物。

问题三：早期技术决策会锁死错误方向

当用户路径还没确认时，提前设计复杂后端，会让后续修改变重。你可能只是想把“处理中”改成“待执行”，但因为状态机、接口、数据库都已经铺开，改动变得复杂。

2.2 什么是纵向切片

纵向切片不是只做前端，也不是只做假数据。它的核心是：沿着一条用户路径，从入口到结果，做出一个可运行、可观察、可验收的小版本。

一个好纵向切片通常包含：

  1. 用户入口：用户从哪里开始；
  2. 核心动作：用户做什么；
  3. 系统反馈：系统给出什么响应；
  4. 状态变化：数据或页面如何变化；
  5. 终点结果：用户看到什么结果；
  6. 验收标准：如何判断成功。

以主案例为例：

2.3 一个好切片的 6 个判断标准

标准一：能看见

用户或产品负责人能在页面上看到结果。如果一个切片做完后只能在代码里看变化，对新手就不友好。

标准二：能操作

用户能执行动作，不是只看静态页面。至少要能输入、点击、确认、取消、查看状态。

标准三：能验收

必须能写出通过/不通过的验收项。例如“输入为空时，生成草案按钮不可点击”。这比“交互要友好”更可验收。

标准四：边界清楚

切片必须写明“不做什么”。例如第一切片不做真实 agent 执行、不做长期记忆、不做多员工调度。

标准五：能接下一片

第一切片做完后，应该自然接第二切片。任务创建闭环之后，可以接审批切片；审批之后，可以接执行结果切片。

标准六：风险可控

如果做错了，能小范围返工，而不是推倒整个系统。

2.4 主案例：为什么不先做“员工配置”

很多人会觉得，既然是 AI 员工系统，第一步应该先设置 AI 员工：员工名称、职责、工具权限、记忆范围、风险等级、工作时间、汇报方式。这些都合理，但不适合作为第一切片。

原因有三点：

  1. **用户价值不直接。**配置员工是为了让员工执行任务。如果任务创建闭环还没跑通，配置员工的价值无法验证。
  2. **字段会无限膨胀。**一旦开始做员工配置，AI 很容易扩展出权限、角色、技能、知识库、工具市场、审批策略。
  3. 验收难度高。“员工职责配置是否合理”很难在第一版验收。但“任务能否创建并进入列表”很容易验收。

因此，第一切片选择任务创建，而不是员工配置。

产品合同不是为了限制想象力

很多人会担心：只写一页纸，会不会把产品想小了？答案是不会。产品合同限制的不是长期想象力，而是第一版施工范围。你可以有很大的愿景，但第一版必须小到可验证。

一个成熟的做法是把内容分成两层：

长期愿景：
AI 员工能像真实员工一样承担任务、调用工具、总结经验。

第一版合同：
只做任务创建与草案确认闭环。

这样既保留了方向，又不会让 coding agent 一开始就冲向完整系统。

成功标准改写训练

下面是一些常见虚标准及改写方式：

虚标准可验收改写
系统要好用用户 3 分钟内能完成第一条任务创建
页面要高级页面包含清晰标题、输入区、草案区、列表区，主要按钮可见
AI 要智能草案至少包含标题、目标、交付物、风险等级
系统要稳定连续创建 5 条任务不报错

你会发现，可验收标准往往更朴素，但更能指导开发。

待确认项的价值

待确认项不是“没想清楚”的羞耻记录，而是防止 AI 脑补的保险箱。例如你暂时不知道是否支持附件，不要让 AI 自己决定。写成：

待确认：第一版是否支持附件上传？
风险：如果 AI 自行实现附件，会引入文件存储和安全问题。
默认处理：第一版不支持附件，只保留后续扩展位。

这种写法能直接降低范围失控风险。

v0.3 扩写：产品合同是开发前的最低约定

很多新手不喜欢写产品合同，觉得这是“文档工作”，不如直接让 AI 写页面或写代码。但在 AI 协同开发里，产品合同不是传统意义上的厚 PRD，而是一张很短的“开发约束纸”。

它的作用不是证明你想得多完整，而是回答三个问题：

  1. 这次到底要解决谁的什么问题？
  2. 这一版用户要走完哪条流程？
  3. 哪些事情明确不做？

只要这三个问题没有说清楚，AI 就会替你做决定。

3.1 为什么叫“产品合同”

“合同”这个词很重要。它意味着这不是随便写写的想法，而是你和 AI、你和 coding agent、你和未来自己的最低约定。产品合同要做到：后续页面预览必须依据它；后续施工任务单必须依据它；后续验收清单必须依据它；后续返工时也要回到它。

如果产品合同里没有写“本版不做审批”，coding agent 做出审批入口，你就很难说它错了。因为你没有提前约束。如果产品合同里写了“本版不做审批”，那这就是越界实现，可以要求删除或隔离。

3.2 产品合同和 PRD 的区别

对比项一页纸产品合同传统 PRD
目标锁定当前切片描述完整产品
篇幅1 页左右多页甚至几十页
读者自己、GPT、coding agent产品、设计、研发、测试等团队
重点用户、流程、边界、验收功能、交互、规则、数据、版本等
适合阶段AI 协同开发早期团队协作和成熟产品阶段

本书不是反对 PRD，而是告诉新手：在第一切片之前，不要急着写厚 PRD。先写一页纸产品合同，让范围可控。

3.3 一份合格产品合同的 8 个字段

字段 1：功能名称

差的写法：

AI 员工系统

好的写法：

AI 员工任务创建与草案确认闭环

区别在于，后者天然限制了范围。

字段 2：目标用户

写清楚谁使用，不要写“所有用户”。主案例中，第一版目标用户是任务发起人 / 管理者。这个人希望把一个任务交给 AI 员工，并确认任务已经被系统记录。暂时不是 AI 员工管理员、团队成员、审计人员或系统运维人员。

字段 3：核心问题

不要写“提高效率”这种空话，要写具体卡点。

差的写法：

帮助用户更高效地使用 AI 员工。

好的写法：

用户有任务想交给 AI，但不知道如何把任务描述变成一条可确认、可追踪的系统任务。

字段 4：本版闭环

写成链路：起点 → 系统反馈 → 用户确认 → 终点。

用户输入任务描述 → 系统生成任务草案 → 用户编辑并确认 → 任务进入列表，状态为“待执行”。

字段 5：成功标准

每条都要能验收。差的写法是“页面体验好，任务创建方便”。好的写法是：

1. 空输入时不能生成草案。
2. 输入任务后能生成包含标题、目标、补充信息的草案。
3. 草案内容可以编辑。
4. 点击确认后，任务进入列表。
5. 列表中显示任务标题、创建时间、状态“待执行”。

字段 6：本版做什么

明确范围：任务输入框、生成草案按钮、草案展示和编辑、确认创建任务、任务列表展示、基础错误提示。

字段 7：本版不做什么

这是产品合同里最容易被忽视、但最关键的字段。

- 不接真实 agent 执行
- 不做真实工具调用
- 不做高风险审批
- 不做长期记忆
- 不做多员工调度
- 不做复杂权限
- 不做数据库持久化，第一轮可用 mock 或本地状态

字段 8：待确认项

不确定的内容不要让 AI 脑补，先放这里。

- 草案是否需要风险等级？
- 任务类型是否需要枚举？
- 是否支持附件？
- 任务列表是否需要筛选？

待确认项不是阻碍开发，而是防止模型自作主张。

3.4 主案例产品合同扩写示例

# 一页纸产品合同：AI 员工任务创建与草案确认闭环

## 1. 功能名称
AI 员工任务创建与草案确认闭环。

## 2. 目标用户
任务发起人 / 管理者。用户希望把一个任务交给 AI 员工处理，但在任务正式进入系统前，需要先看到一份可编辑的任务草案。

## 3. 核心问题
用户直接输入自然语言任务时，常常描述不完整、不结构化，也不知道任务是否已经被系统记录。本功能要帮助用户把模糊任务描述转成一条可确认、可追踪的任务记录。

## 4. 本版闭环
用户输入任务描述 → 系统生成任务草案 → 用户编辑草案 → 用户确认创建 → 任务进入列表，初始状态为“待执行”。

## 5. 本版做什么
- 提供任务描述输入框。
- 提供“生成草案”按钮。
- 显示任务草案，包括任务标题、任务目标、补充说明。
- 草案字段可编辑。
- 提供“确认创建任务”按钮。
- 确认后任务进入列表。
- 列表显示标题、创建时间、状态。
- 处理空输入和生成失败提示。

## 6. 本版不做什么
- 不执行真实任务。
- 不接真实 AI agent。
- 不调用外部工具。
- 不做审批流。
- 不做多员工分配。
- 不做长期记忆。
- 不做复杂权限。
- 不做数据库持久化。

## 7. 成功标准
- 空输入时不能点击生成草案，或点击后明确提示用户输入任务描述。
- 输入有效任务后，可以生成草案。
- 草案字段可以编辑。
- 点击确认后，任务列表新增一条任务。
- 新任务状态显示为“待执行”。
- 页面不出现本版不做范围内的入口，例如员工配置、权限配置、计费模块。

## 8. 待确认项
- 是否在草案中显示风险等级？第一版暂不显示。
- 是否需要任务类型？第一版暂不需要。
- 是否支持附件？第一版不支持。
- 页面刷新后是否保留数据？第一版不要求。

3.5 产品合同常见错误

  1. 目标用户太宽。“所有想使用 AI 员工的人”会导致功能扩张。第一版要具体到一个角色。
  2. 成功标准不可检查。“让用户体验丝滑”不是验收项。要改成可观察行为，例如“最多 2 次点击完成任务创建”。
  3. **本版不做为空。**不写不做项，等于默认 AI 可以自由扩展。
  4. **技术实现抢跑。**产品合同阶段不需要写 Redis、PostgreSQL、微服务、LangGraph 或向量数据库。
  5. **待确认项被隐藏。**不确定就显性列出，等真正需要时再决策。

页面预览阶段不要急着追求漂亮

新手常犯的一个错误是，把页面预览理解成 UI 设计，开始纠结颜色、圆角、阴影、动效。视觉当然重要，但第一轮页面预览更重要的是：信息有没有放对，路径有没有走通，状态有没有反馈。

你可以先问这几个问题：

  • 用户进来第一眼知道这是干什么的吗？
  • 用户知道第一步要输入什么吗？
  • 主要按钮在哪里？
  • 点击按钮后页面会发生什么？
  • 失败时用户知道怎么处理吗？
  • 没有数据时页面如何引导？

如果这些问题没解决，页面再漂亮也不好用。

页面预览的三层

第一层：信息层

页面上有哪些信息？例如任务标题、目标、交付物、风险等级、状态。

第二层：动作层

用户能做什么？例如生成草案、重新生成、编辑草案、确认创建。

第三层：反馈层

用户操作后系统如何反馈？例如 loading、成功提示、错误提示、按钮禁用。

三层缺一不可。很多页面“不好用”，不是因为缺功能，而是缺反馈。

主案例页面路径更细示例

1. 用户进入任务创建页；
2. 看到说明文案，知道要输入任务；
3. 输入框为空时，生成按钮禁用；
4. 输入任务后，按钮变为可点击；
5. 点击后按钮显示“生成中……”；
6. 成功后出现草案卡片；
7. 用户编辑标题或交付物；
8. 点击确认创建；
9. 顶部出现成功提示；
10. 新任务出现在列表第一行，状态为待执行。

这个路径可以直接变成验收清单。

4.1 页面预览解决什么问题

问题一：用户从哪里开始

如果用户打开页面不知道第一步该做什么，后端再强也没用。主案例第一切片中，用户第一步应该非常明确：在任务输入框中描述希望 AI 员工完成的任务。页面上应该有明显输入区和生成草案按钮。

问题二：系统反馈是什么

用户点击“生成草案”后，页面应该显示 loading 文案、草案卡片、错误提示或空状态说明？这些都属于页面预览阶段要确认的内容。

问题三：用户如何确认

AI 生成草案后，用户不能被迫直接提交。页面应该支持查看草案、编辑草案、取消、确认创建。这体现了本书强调的“人工确认点”。

问题四：结果如何承接

确认后任务进入哪里？列表显示哪些字段？状态是什么？用户能否点开详情？这些决定了闭环是否完整。

4.2 页面预览不是视觉稿

页面预览的第一目标是验证信息是否完整、操作路径是否顺、状态是否可理解、边界是否覆盖、是否出现越界功能。视觉风格可以先简单，但结构要清楚。

本章定位：核心训练章节

本章你要学会什么

你要掌握从大系统想法中找出第一条最值得打通的小闭环。最小闭环不是最小功能，而是最小可验证业务链路。

为什么这一章重要

AI 协同开发最容易失败的地方，往往不是模型不会写代码，而是人没有把目标、边界、检查点和验收方式定义清楚。本章的作用，是把一个容易凭感觉推进的环节，变成可以重复执行的训练动作。你不需要一开始掌握传统软件工程的全部知识，但你必须能把 AI 的输出限制在自己能审查、能判断、能返工的范围内。

核心概念

  • 最小闭环：起点、过程、终点都清楚的小业务链路。
  • 第一切片：准备交给 coding agent 的第一个可运行闭环。
  • 起点动作：用户首先做什么。
  • 终点结果：用户最终看到什么。
  • 人工确认点：AI 早期开发的重要安全带。
  • 切片边界：做什么、不做什么。

核心观点

  1. 最小闭环不是最小按钮，而是最小业务链路。
  2. 第一切片优先选择用户看得见价值的链路。
  3. 起点和终点不清，切片就不可控。
  4. 第一切片不追求自动化最高，而追求验证方向最快。
  5. 人工确认不是落后，而是防止 AI 误执行。

主案例推进

完整 AI 员工系统包含任务、审批、执行、记忆、工具权限、复盘。但第一切片选：用户输入任务 → AI 生成任务草案 → 用户编辑/确认 → 任务进入列表 → 显示待执行状态。

错误示范

先实现完整角色系统、工具权限、任务调度和长期记忆。

这不可见、不可快速验收，而且复杂依赖太多。

正确示范

先实现任务创建小闭环：输入任务、生成草案、编辑确认、进入列表。草案生成和数据保存都可以先 mock。

方法拆解

1. 写出完整想法

先允许自己写大，但不要直接施工。

2. 找用户最早动作

用户第一次打开系统最想做什么？主案例是交代任务。

3. 找可见结果

用户交代任务后，至少要看到系统理解出的任务草案和任务列表。

4. 加入人工确认

AI 生成草案后先让用户确认，避免误解后直接执行。

5. 定义终点

确认后任务进入列表，状态为待执行。

6. 写边界

做输入、草案、确认、列表；不做执行、工具、记忆、审批、权限。

和 GPT 的对话演示

请不要展开完整系统。请从 AI 员工系统中识别 5 个候选最小闭环，并推荐第一切片。每个闭环包含起点、终点、用户价值、复杂度、是否可 mock、是否可验收。

深入训练：用“四问法”逼出最小闭环

当你面对一个大想法时，可以连续问四个问题。

第一问：用户第一次来，最想完成什么动作？

不要回答“使用系统”。要回答具体动作。主案例中是“创建一条 AI 员工任务”。

第二问：用户完成这个动作后，必须看到什么结果才觉得有价值？

主案例中不是“AI 完成任务”，而是“系统生成了可确认的任务草案，并把确认后的任务放入列表”。这是一个更小、更可控的结果。

第三问：哪些复杂能力可以先假装存在？

主案例中，真实 AI 执行可以先不做，真实模型生成草案也可以先 mock，长期记忆可以先不做，审批可以先放后续。

第四问：如果只做这条链路，用户是否能判断方向对不对？

如果答案是能，这就是好第一切片。如果答案是不能，说明切片可能太偏基础设施。

主案例第一切片详细边界

必须做

1. 任务输入框；
2. 生成任务草案按钮；
3. 生成中状态；
4. 草案展示卡片；
5. 草案字段可编辑；
6. 确认创建按钮；
7. 任务列表；
8. 任务初始状态“待执行”。

可以简化

1. 草案生成可以用 mock 规则；
2. 任务数据可以只存在前端状态；
3. 风险等级可以先用低/中/高三档；
4. 任务详情可以先用展开区域，不做独立页面。

明确不做

1. 不做真实任务执行；
2. 不接工具调用；
3. 不做长期记忆；
4. 不做多员工调度；
5. 不做复杂权限；
6. 不做真实审批流；
7. 不做消息通知；
8. 不做后端持久化。

coding agent 容易越界的地方

1. 自行创建员工配置页面；
2. 自行加入审批中心；
3. 自行设计权限模型；
4. 自行接入真实 LLM API；
5. 自行设计数据库表；
6. 自行增加登录注册。

这些内容不是永远不做，而是不属于第一切片。

读者常见错误拆法

错误拆法 1：先做基础能力

先搭好 agent 框架、记忆系统、权限系统，再做任务创建。

问题是基础能力无法被普通用户直接验证。你会花很多时间做看不见的东西。

错误拆法 2：先做最炫能力

先让 AI 自动执行任务，展示智能效果。

问题是依赖太多，错误来源太复杂。到底是任务理解错了、工具调用错了、权限错了，还是执行逻辑错了，很难判断。

错误拆法 3：先做配置中心

先让用户配置员工职责、技能、工具权限。

问题是没有真实任务时，配置项很容易拍脑袋。

训练：把自己的项目压成一句话切片

格式：

用户【做一个动作】后，系统【给出中间反馈】，用户【确认/选择/编辑】后，系统【给出可见结果】。

主案例填法：

用户输入任务后，系统生成任务草案，用户编辑确认后，系统把任务放入列表并显示待执行。

外贸案例填法：

用户输入目标国家和产品后，系统生成候选客户列表，用户查看匹配理由后，标记值得跟进的客户。

教育案例填法：

学生完成一组练习后，系统生成错题清单，老师确认后，系统推荐下一组针对性练习。

v0.2 核心训练扩写：把“大想法”压成第一条能跑通的链路

本节是对第 5 章的扩写。目的不是多讲概念，而是把“识别最小闭环”训练成一套可以反复使用的动作。

5.1 先纠正一个常见误解：最小闭环不是“最小功能”

很多新手听到“最小闭环”，第一反应是：那我是不是只做一个按钮？只做一个输入框？只做一个页面？

这就是第一个误解。

最小闭环不是把功能拆到最小，而是把业务链路拆到最短。

一个按钮本身不构成闭环。一个输入框也不构成闭环。一个页面也不一定构成闭环。闭环至少要回答三个问题：

  1. 用户从哪里开始？
  2. 用户中间做了什么关键动作？
  3. 用户最后看到了什么可判断的结果？

例如，在 AI 员工任务系统里，“做一个任务输入框”不是闭环。因为用户输入以后，没有看到系统怎么理解任务，也没有看到任务是否被创建。

更好的闭环是：

用户输入任务 → 系统生成任务草案 → 用户确认 → 任务进入列表 → 状态显示为待执行

这条链路虽然简单，但已经能回答一个核心问题：用户能不能把一个任务稳定交给 AI 员工系统。

只要这个问题被验证，后续审批、执行、记忆、工具调用才有意义。反过来，如果这个最基本的交付任务动作都不好用，你提前做再复杂的权限系统、记忆系统、调度系统，都会变成“看起来完整，但核心体验不成立”。

5.2 好闭环的 6 个判断标准

判断一个闭环能不能作为第一切片，可以用下面 6 个标准。

标准 1：有明确起点

起点必须是用户看得懂、做得出来的动作。

不好的起点：

系统初始化 agent 能力。

这个起点对用户不可见，也不容易验证。

好的起点：

用户在任务输入框里输入一句自然语言任务。

这个起点清楚、可操作、可测试。

标准 2：有明确终点

终点必须是一个用户能看见的结果。

不好的终点：

系统完成任务调度。

调度是否完成，新手很难直接判断。

好的终点：

任务出现在任务列表中，状态显示为“待执行”。

这个结果可见、可截图、可验收。

标准 3：中间路径短

第一切片不要经过太多系统模块。路径越长，问题越难定位。

不好的路径：

输入任务 → 匹配员工 → 查询记忆 → 判断权限 → 调用工具 → 执行任务 → 汇总结果 → 写复盘

这个链路看起来完整，但对第一轮开发太长。

好的路径：

输入任务 → 生成草案 → 人工确认 → 入列表

第一轮先验证“任务能否被正确创建”。

标准 4：能 mock

第一切片最好可以用 mock 数据跑起来。

这不是偷懒，而是降低依赖。因为早期真正要验证的是页面流程、状态变化、用户理解，而不是复杂模型能力。

主案例中，任务草案可以先用规则或固定 mock：

用户输入：帮我整理本周客户开发情况
系统草案：
- 任务标题：整理本周客户开发情况
- 任务目标：汇总本周客户开发进展
- 预期产出：一份简要总结
- 风险等级：低

即使这个草案不是由真实 agent 生成，也能先验证草案展示、编辑、确认、入列表这一整条体验。

标准 5：能验收

一个好切片必须能写出验收标准。

如果你写不出验收标准，说明这个切片还不够清楚。

例如：

成功标准：用户输入任务后，点击“生成草案”，页面出现可编辑草案；点击“确认创建”，任务进入列表，状态为“待执行”。

这就是可验收的表达。

不好的表达是：

系统要智能地理解用户任务。

“智能”很难验收。“理解”也容易变成主观感觉。

标准 6：后续能自然接下一切片

第一切片不是孤立的，它要给第二切片留下接口。

主案例的第一切片结束于“任务进入列表，状态为待执行”。这正好可以接第二切片：

任务风险判断 → 高风险进入审批 → 用户批准或拒绝 → 状态更新

如果第一切片的终点设计得好，后续切片就像接积木一样自然。

5.3 主案例第一轮：从完整系统到候选闭环

我们先把完整想法写出来：

我想做一个 AI 员工系统。它有员工角色、职责、记忆、工具权限、任务调度、审批、执行、复盘。管理者可以给 AI 员工分配任务，AI 员工自主执行，并在高风险操作前请求人工审批。

这个想法很大。现在不要急着让 GPT 写完整 PRD。先列候选闭环。

候选闭环 A：任务创建闭环

用户输入任务 → 系统生成草案 → 用户确认 → 任务进入列表

价值：用户能把任务交给系统。
可见性：高。
复杂度：低。
是否可 mock：是。
是否适合第一切片：非常适合。

候选闭环 B：审批闭环

系统识别高风险任务 → 进入审批队列 → 用户同意或拒绝 → 更新任务状态

价值：控制风险。
可见性：高。
复杂度：中。
是否可 mock：是。
是否适合第一切片：不如 A，因为它依赖任务已经存在。

候选闭环 C：执行结果闭环

任务执行 → 生成结果 → 用户查看 → 标记满意或需要返工

价值：接近最终业务价值。
可见性：高。
复杂度：中高。
是否可 mock：部分可以。
是否适合第一切片：不适合第一轮，因为真实执行依赖太多。

候选闭环 D：员工配置闭环

用户创建 AI 员工 → 设置职责、工具权限、风险规则 → 保存配置

价值：为系统长期运行打基础。
可见性：中。
复杂度：中。
是否可 mock：是。
是否适合第一切片：不建议，因为它是配置型功能，不能直接证明用户能完成任务交付。

推荐结果

第一切片选 A：任务创建闭环。

理由很简单：它是 AI 员工系统的入口动作。没有任务创建，就没有审批、执行、复盘。它用户可见、容易 mock、验收清楚、后续能自然接审批切片。

5.4 主案例第二轮：把第一切片收紧

确定候选闭环后，还要继续收紧。否则 coding agent 仍然可能扩展。

第一版切片描述：仍然有点大

实现 AI 员工任务创建功能，用户可以创建任务，AI 员工理解任务并开始执行。

问题：

  • “AI 员工理解任务”不够可验收。
  • “开始执行”会引入真实 agent、工具调用和任务队列。
  • 没有说明是否需要数据库。
  • 没有说明页面范围。

第二版切片描述：更清楚

实现任务创建第一切片：用户输入任务描述，系统生成一个可编辑的任务草案；用户确认后，任务进入任务列表，初始状态为“待执行”。本切片使用 mock 草案生成和前端本地状态，不接真实 agent，不接真实后端，不做审批和执行。

这一版明显更可施工，因为它写清了：

  • 起点：用户输入任务描述。
  • 过程：生成可编辑任务草案。
  • 终点：进入任务列表，状态为待执行。
  • 数据策略：mock 草案生成，本地状态。
  • 不做：真实 agent、后端、审批、执行。

这就是可以交给 coding agent 的第一切片定义。

5.5 三组错误问法 vs 正确问法

组 1：从完整系统开始

错误问法：

我要做一个 AI 员工系统，请直接帮我规划完整功能和开发步骤。

问题：GPT 会自动扩展角色、记忆、工具、调度、权限、日志、部署等内容。材料会变多，但你很难判断第一步到底该做什么。

正确问法：

我想做一个 AI 员工系统。请不要展开完整功能。请只帮我识别 3 个候选最小闭环，每个闭环写清起点、终点、用户价值、复杂度和是否适合第一切片。

组 2：切片边界不清

错误问法：

先做任务创建功能。

问题：“任务创建”可能包含自然语言理解、任务拆解、员工分配、入库、执行触发、通知等一堆内容。

正确问法：

请只做任务创建第一切片：输入任务 → 生成可编辑草案 → 用户确认 → 进入任务列表。不要实现员工分配、真实执行、审批、通知、长期记忆。

组 3：没有验收导向

错误问法：

帮我把这个功能做得好用一点。

问题：“好用”对 coding agent 不够明确。

正确问法：

5.12 读者常见卡点

卡点 1：总觉得第一切片太简单，不像产品

很多人会担心：只做任务创建，会不会太简陋？

你要记住，第一切片的目的不是证明系统已经完整，而是证明方向没有偏。第一切片像修路时打通第一段通道。它不代表高速公路建完了，但它能证明路线是对的。

卡点 2：忍不住把审批也放进第一切片

审批很重要，但它依赖任务已经存在。如果你把任务创建和审批同时放进第一切片，问题会变多：到底是任务创建不好，还是审批规则不好？到底是状态设计不好，还是按钮位置不好？

第一轮先让任务能稳定进入列表。第二轮再做审批。

卡点 3：分不清“可 mock”和“假功能”

mock 不是假装完成产品，而是用低成本方式验证流程。

如果你明确写出“本切片使用 mock 草案生成，不验证真实 agent 能力”，它就是合理的开发策略。问题不在于 mock，而在于没有说明 mock 的边界，导致自己以为已经实现真实能力。

卡点 4：不知道怎么判断终点

终点最好满足三个条件：

  1. 用户能看到。
  2. 可以截图。
  3. 可以写成验收项。

如果一个终点不能截图，通常说明它太偏系统内部。

第 6 章：如何给 GPT 下达切片任务，让它不发散

版本：v0.2 核心训练扩写版
本章定位：核心训练章节

本章你要学会什么

你要学会把 GPT 从自由发挥模式拉回切片协作模式。好提示词的核心不是更长，而是边界更清楚。

为什么这一章重要

AI 协同开发最容易失败的地方，往往不是模型不会写代码，而是人没有把目标、边界、检查点和验收方式定义清楚。本章的作用，是把一个容易凭感觉推进的环节，变成可以重复执行的训练动作。你不需要一开始掌握传统软件工程的全部知识，但你必须能把 AI 的输出限制在自己能审查、能判断、能返工的范围内。

核心概念

  • 输出边界：本轮输出什么、不输出什么。
  • 禁止展开：防止 GPT 写后端、数据库、权限等内容。
  • 待确认项：不确定内容不脑补。
  • 单轮目标：每次只让 GPT 完成一种任务。
  • 验收导向：把描述改成可检查表达。

核心观点

  1. GPT 默认倾向补全和扩展，必须显式限制。
  2. 好提示词不是更长，而是规定本轮只做什么。
  3. 每轮只完成一种任务。
  4. 让 GPT 列待确认项，比让它默默脑补更安全。
  5. 要把感觉不对改成明确约束。

主案例推进

围绕第一切片，与 GPT 的对话应分轮：审查产品合同、输出页面预览、收紧切片边界、生成施工单、生成验收清单。每轮只做一件事。

这些都容易发散，因为没有边界、没有输出格式、没有禁止展开。

正确示范

请只围绕“任务创建 → 草案确认 → 任务进入列表”这个第一切片工作。
不要展开审批、执行、记忆、工具调用、权限。
本轮只输出页面预览、切片边界、待确认项。

方法拆解

1. 写背景

一句话说明项目和当前切片。

2. 写本轮目标

例如本轮只输出页面预览。

3. 写禁止范围

列出不做审批、执行、记忆、权限等。

4. 写输出格式

规定标题和字段，减少自由发挥。

5. 要求待确认项

所有不确定内容放待确认项。

6. 要求可验收

所有标准都改成能手工检查。

禁止：后端、数据库、接口、审批、执行、长期记忆、权限。

提示词的“刹车系统”

给 GPT 的提示词里，要有刹车。刹车不是一句“不要发散”就够了，而是具体写清楚什么叫发散。

例如：

以下内容视为发散：
1. 写数据库设计；
2. 写后端接口；
3. 设计权限系统；
4. 加入员工配置；
5. 讨论部署；
6. 设计长期记忆。

这样 GPT 才知道边界在哪里。

三种常用收敛句式

句式 1：只做当前层

本轮只做页面预览，不写代码、不写接口、不写数据库。

句式 2：只做当前切片

本轮只围绕任务创建与草案确认，不展开审批、执行、记忆、权限。

句式 3：不确定就问

无法从材料中确定的内容，请放入待确认项，不要替我做默认决定。

这三句话可以组合使用。

“继续”之前先指定方向

新手常说“继续”，但 GPT 不知道继续哪里。你要把“继续”改成下面几种：

继续扩写验收清单，不要写实现。
继续补充异常流程，不要改正常流程。
继续审查越界功能，不要重写方案。
继续把成功标准改成可验收表达。
继续把页面预览收敛成施工单。

这样 GPT 的输出会稳定很多。

第 3 轮：收敛施工边界

基于页面预览，请输出第一切片边界。
只写本切片做什么、不做什么、哪些可以 mock、验收标准。
不要写代码。

这三轮的顺序非常重要。不要跳过前两轮直接施工。

GPT 输出越界时的修正话术

你刚才的输出中包含了本切片不做的内容，例如【列出】。
请重新输出，只保留任务创建与草案确认闭环。
把审批、执行、权限、记忆放到“后续切片”，不要展开。

注意不要直接说“你错了，重写”。要明确指出哪里越界、如何处理。

每次发送提示词前，快速检查：

v0.2 核心训练扩写：让 GPT 围绕当前切片工作

本节扩写第 6 章。目标是把“会提问”变成“会控制输出边界”。

6.1 你不是在问 GPT，而是在给它划施工边界

很多新手把 GPT 当成一个“懂很多的顾问”。遇到一个想法，就问：

你觉得这个系统应该怎么做？

GPT 会回答，而且通常回答得很完整。但完整不等于适合当前阶段。

在 AI 协同开发里，你更应该把 GPT 当成一个非常能干、但容易主动扩展的协作者。它会补全你没说的内容，会替你做很多假设，会把一个小需求扩成一个完整系统。

所以，你给 GPT 的任务不能只写“我要什么”，还要写：

  1. 本轮只做什么。
  2. 本轮不要做什么。
  3. 输出格式是什么。
  4. 哪些内容必须放入待确认项。
  5. 哪些内容不能自行决定。

这不是为了限制 GPT 的能力，而是为了让它的能力服务于你当前的切片。

6.2 切片任务提示词的基本结构

一个稳定的切片任务提示词，建议包含 7 个部分。

1. 角色：你希望 GPT 以什么身份工作。
2. 背景：项目是什么，当前阶段是什么。
3. 当前切片：本轮只围绕哪条链路。
4. 明确禁止：哪些内容不要展开。
5. 输出目标：本轮要产出什么。
6. 输出格式：按什么结构输出。
7. 待确认项：不确定时不要脑补，列出来。

主案例示范：

你是一名 AI 协同开发教练，擅长帮助新手把模糊需求压缩成可施工切片。

项目背景：我在做一个 AI 员工任务系统。完整系统未来可能包含任务创建、审批、执行、记忆、工具权限和复盘。

当前切片：只围绕“用户输入任务 → 系统生成可编辑草案 → 用户确认 → 任务进入列表”工作。

明确禁止：不要展开真实 agent 执行、工具调用、多员工调度、长期记忆、复杂权限、数据库设计和部署方案。

输出目标：请帮我输出当前切片的页面预览、切片边界和待确认项。

输出格式：
1. 页面范围
2. 用户路径
3. 页面状态
4. 本切片做什么
5. 本切片不做什么
6. 待确认项

要求：所有你不确定的地方都放入待确认项，不要自行决定。

这个提示词看起来比一句话长，但它能显著降低 GPT 发散的概率。

6.3 “禁止展开”不是客气话，要写具体

很多人会在提示词里写：

不要太复杂。

这句话几乎没用。因为“复杂”是主观词。GPT 不知道你认为哪些内容复杂。

更好的写法是列出具体禁止项：

不要展开以下内容：
1. 真实 agent 执行。
2. 工具调用。
3. 多员工调度。
4. 长期记忆。
5. 高风险审批。
6. 权限系统。
7. 数据库设计。
8. 部署方案。

具体禁止项的好处是：

  • GPT 更容易遵守。
  • 你更容易检查输出是否越界。
  • 后续转成施工单时，coding agent 也更不容易顺手加功能。

6.4 三组错误问法 vs 正确问法

组 1：目标太大

错误问法：

请帮我设计一个 AI 员工系统。

可能输出：角色系统、任务系统、工具系统、记忆系统、权限系统、日志系统、部署架构。

正确问法：

请不要设计完整 AI 员工系统。请只围绕第一切片“任务创建 → 草案确认 → 进入列表”工作，输出页面预览和切片边界。

组 2：输出物不清

错误问法：

帮我分析一下这个功能。

问题：GPT 可能写市场分析、产品分析、技术分析、风险分析，但你当前需要的是可执行材料。

正确问法：

请把下面的功能改写成一页纸切片定义，字段包括：起点、终点、用户路径、做什么、不做什么、验收标准、待确认项。

组 3：让 GPT 默默脑补

错误问法：

缺的地方你自己补充。

这句话非常危险。GPT 会替你决定很多关键边界。

正确问法：

所有不确定或需要业务决策的地方，请放入“待确认项”，不要自行补充成确定方案。

练习 1：识别发散提示词

判断下面哪些提示词容易发散。

A. 请帮我设计完整 AI 员工系统。
B. 请只围绕任务创建第一切片输出页面状态。
C. 请把这个功能做成完整产品方案。
D. 请不要写架构，只输出验收清单。
E. 缺的你帮我补全。

参考答案：

容易发散：A、C、E。
不容易发散：B、D。

解释：A 和 C 范围过大；E 允许 GPT 脑补。B 和 D 明确限制了范围和输出物。

练习 2：改写发散提示词

原提示词：

我要做一个外贸获客系统，请帮我设计完整方案。

参考改写：

我想做外贸获客系统。请不要设计完整方案。请只识别第一条最小闭环：用户输入目标国家和产品 → 系统生成候选客户列表 → 用户标记是否值得跟进。请输出起点、终点、做/不做边界和验收标准。

练习 3：限制输出范围

参考答案：

当前只做第一切片“任务创建 → 草案确认 → 入列表”。不要展开审批、执行、员工配置、权限、记忆、数据库、部署。所有涉及这些内容的想法请放入“后续切片建议”，不要写进当前方案。

练习 4：要求待确认项

参考答案：

如果你发现材料中缺少业务规则，请不要自行决定。请统一放入“待确认项”，格式为：问题、为什么需要确认、如果不确认可能导致什么偏差。

练习 5：页面预览提示词

参考答案：

基于下面的一页纸产品合同，请只输出页面预览方案，不要写后端、数据库和接口。页面预览必须包括页面区块、按钮、用户点击路径、空状态、加载态、错误态和待确认项。

练习 6：验收清单提示词

参考答案：

请基于当前切片生成手工验收清单。每条验收项必须包含：前置条件、操作步骤、期望结果、通过标准。请覆盖正常流程、空输入、加载失败、重复点击和本版不应出现的越界功能。

练习 7：连续三轮对话设计

参考答案：

第一轮：请把模糊需求压缩成最小闭环。
第二轮：请基于最小闭环输出页面预览，不要写后端。
第三轮：请基于页面预览输出切片边界和验收标准，不要写代码。

这三轮的关键是：每一轮只要一个输出物。

练习 8：分析 GPT 输出是否越界

示例输出：

除了任务创建页，还需要设计员工权限表、任务执行队列、工具调用日志和部署架构。

参考答案：

越界内容：员工权限表、任务执行队列、工具调用日志、部署架构。
处理方式：从当前切片删除，放入后续阶段。
原因：当前切片只验证任务创建到入列表，不需要这些技术模块。

6.13 读者常见卡点

卡点 1：提示词写太短，结果失控

短提示词不是问题，问题是缺少边界。如果你只说“帮我设计一下”，GPT 会默认补全。

卡点 2：提示词写很长，但没有本轮目标

有些人把很多背景都贴进去，但不说这轮要什么。GPT 仍然会发散。

卡点 3：怕限制太多影响 GPT 发挥

早期开发不是头脑风暴，而是施工控制。你可以单独开一轮让 GPT 发散，但一旦进入切片施工，就必须收敛。

卡点 4：把 GPT 的输出当最终答案

GPT 输出是草稿，不是命令。你要用越界检查表审查它。

6.15 本章小结补强

GPT 很强，但它不会自动知道你当前处在哪个开发阶段。你必须告诉它：本轮只做什么，不做什么，输出什么，不确定时怎么处理。

本章你要学会什么

你要学会把产品切片转成 coding agent 能执行的施工任务单。施工单不是 PRD，而是一次清晰的施工命令。

为什么这一章重要

AI 协同开发最容易失败的地方，往往不是模型不会写代码，而是人没有把目标、边界、检查点和验收方式定义清楚。本章的作用，是把一个容易凭感觉推进的环节，变成可以重复执行的训练动作。你不需要一开始掌握传统软件工程的全部知识，但你必须能把 AI 的输出限制在自己能审查、能判断、能返工的范围内。

核心概念

  • 施工任务单：面向 coding agent 的单次开发指令。
  • 输入：产品合同、页面预览、切片边界。
  • 输出：本次必须交付的页面、状态、数据。
  • 约束：不做项和技术限制。
  • 验收标准：完成后逐条对照。
  • 变更文件清单：说明改了什么。

核心观点

  1. 施工单只做一个切片。
  2. 施工单必须写清不做什么。
  3. 施工单必须要求完成后汇报。
  4. 施工单越清楚，返工越可控。
  5. 不要把完整 PRD 原样丢给 coding agent。

施工单和普通提示词的区别

普通提示词可以用于讨论，施工单用于执行。讨论时可以开放一点，施工时必须收敛。施工单必须回答 coding agent 最关心的几个问题：

  • 我这次到底改什么？
  • 我参考哪些材料？
  • 哪些文件或页面可能相关？
  • 哪些功能不能碰？
  • 做完如何证明完成？
  • 如果需求不清楚怎么办？

如果这些问题没写清，coding agent 就会用自己的判断补全。

施工单里的“不做项”要写得像禁止清单

不要只写“不要发散”。要写具体：

本次不做：
1. 不做真实 AI 执行；
2. 不接工具调用；
3. 不新增审批页面；
4. 不新增员工配置页；
5. 不引入登录注册；
6. 不设计数据库；
7. 不改全局路由；
8. 不重构无关组件。

越具体，越安全。

施工单里的验收标准要能让 coding agent 自查

不要只写：

功能正常。

要写：

1. 空输入时生成按钮禁用；
2. 输入任务后可生成草案；
3. 草案字段可编辑；
4. 点击确认后任务进入列表；
5. 列表状态显示“待执行”；
6. 页面不出现审批、权限、员工配置等入口。

这样 coding agent 完成后可以逐条汇报。

完成后汇报格式很重要

很多人只让 coding agent 写代码，不要求汇报。结果你不知道它改了哪里，也不知道哪些验收项通过了。建议每次施工单最后都加：

完成后请回复：
1. 本次完成了什么；
2. 新增/修改/删除了哪些文件；
3. 如何运行和查看；
4. 对照验收清单逐条说明是否通过；
5. 已知问题；
6. 是否有任何超范围改动。

这能显著降低审查难度。

本节扩写第 7 章。目标是让读者能写出“Codex / Claude Code 看了就能开工、做完后你也能验收”的施工任务单。

7.1 施工任务单不是 PRD

很多新手会把 PRD、产品想法、技术方案、开发命令混在一起给 coding agent。

例如：

我想做一个 AI 员工系统，支持任务创建、审批、执行、记忆、权限、日志。请你帮我实现。

这不是施工单。这只是一个大愿望。

施工单的特点是：

  1. 只面向一次施工。
  2. 只完成一个切片。
  3. 输入材料明确。
  4. 输出物明确。
  5. 约束明确。
  6. 验收标准明确。
  7. 完成后必须汇报变更文件、运行方式、已知问题。

你可以把施工单理解成：给一个能力很强但不了解你全部意图的施工队下达的“本次只干这些活”的书面命令。

7.2 一张合格施工单的 9 个字段

字段 1：任务标题

标题要表达当前切片，不要写“开发系统”。

推荐：

实现任务创建 → 草案确认 → 入列表前端切片

不推荐：

开发 AI 员工系统

字段 2：任务目标

用 2–3 句话说明本次施工的终点。

字段 3：输入材料

告诉 coding agent 它应该依据哪些材料工作。

例如：产品合同、页面预览、切片边界、验收清单。

字段 4：实现范围

列出要做的内容。

字段 5：明确不做

这是防止发散的关键。

字段 6：技术约束

例如：使用 mock 数据、不接真实后端、不引入新框架、不改无关页面。

字段 7：验收标准

每条都要能手工测试。

字段 8：交付要求

要求 coding agent 完成后汇报：

  • 改了哪些文件
  • 如何运行
  • 如何验证
  • 已知问题
  • 哪些验收项已通过

字段 9：异常处理

如果发现材料冲突或范围不清，应该先列出问题，而不是自行扩展。

7.3 主案例施工单 v1：不合格版本

请根据前面的文档实现 AI 员工系统的任务功能。

问题非常多：

  • “前面的文档”不明确。
  • “任务功能”范围不明确。
  • 没有做 / 不做边界。
  • 没有说明 mock 还是后端。
  • 没有验收标准。
  • 没有要求输出变更说明。

这种施工单很容易导致 coding agent 自行发挥。它可能新建一堆页面，也可能设计数据库，还可能加入权限和审批。最后你会觉得“它写了很多，但不是我要的”。

7.4 主案例施工单 v2：合格版本

# 施工任务单：实现任务创建 → 草案确认 → 入列表前端切片

## 1. 任务目标

请实现 AI 员工任务系统的第一切片：用户输入任务描述，系统生成一个可编辑的任务草案；用户确认后，任务进入任务列表，初始状态显示为“待执行”。

本次只实现前端可交互版本，使用 mock 草案生成和前端本地状态，不接真实后端。

## 2. 输入材料

请依据以下材料施工：
1. 一页纸产品合同：任务创建与确认闭环。
2. 页面预览：任务创建页、草案确认区、任务列表区。
3. 切片边界：只做任务创建、草案确认、任务入列表。
4. 验收标准：见第 6 节。

## 3. 实现范围

请实现：
1. 任务描述输入框。
2. “生成草案”按钮。
3. 空输入时按钮禁用或提交时提示。
4. 点击生成草案后展示加载态。
5. mock 生成任务草案。
6. 草案卡片展示字段：任务标题、任务目标、预期产出、风险等级。
7. 草案字段可编辑。
8. “确认创建”按钮。
9. 确认后任务进入列表。
10. 列表显示任务标题、状态、创建时间。
11. 初始状态为“待执行”。

## 4. 明确不做

请不要实现：
1. 真实 agent 执行。
2. 真实后端接口。
3. 数据库持久化。
4. 高风险审批。
5. 多员工调度。
6. 长期记忆。
7. 工具调用。
8. 权限系统。
9. 通知系统。
10. 部署配置。

## 5. 技术约束

1. 优先在现有项目结构内实现，不要大规模重构。
2. 不要引入新的大型框架，除非项目已使用。
3. mock 数据应集中放置，便于后续替换为真实接口。
4. 不要改动与本切片无关的页面和模块。
5. 如果发现现有代码结构与任务冲突，请先在完成说明中列出，不要自行扩大改造范围。

## 6. 验收标准

1. 页面存在任务描述输入框。
2. 空输入时不能成功生成草案。
3. 输入任务后点击“生成草案”，能看到加载态。
4. 加载结束后出现草案卡片。
5. 草案字段可以编辑。
6. 点击“确认创建”后，任务进入列表。
7. 列表中任务状态为“待执行”。
8. 页面没有出现审批、执行、员工配置、权限等本切片之外功能。

## 7. 完成后请汇报

请在完成后输出：
1. 变更文件清单。
2. 如何运行项目。
3. 如何手工验证每条验收标准。
4. 已知问题。
5. 哪些内容是 mock，后续如何替换。

这就是一张可以给 Codex / Claude Code 的施工单。

7.5 三组错误施工单 vs 正确施工单

组 2：没有交付要求

错误施工单：

7.12 读者常见卡点

卡点 1：不知道技术约束怎么写

你不懂代码也可以写过程约束：不大规模重构、不引入无关依赖、不改无关文件、mock 数据集中放置。这些约束足够有价值。

卡点 2：施工单越写越像 PRD

施工单不是描述未来系统，而是描述本次要改什么。凡是本次不做的，都移出施工单正文，放到后续计划。

卡点 3：不知道怎么要求 agent 汇报

直接固定要求 5 件事：变更文件、运行方式、验收结果、已知问题、mock 说明。

卡点 4：怕不让 agent 发挥会影响质量

施工阶段不需要自由发挥。你可以让它在完成说明中提出建议，但不要让它直接顺手改。

本章你要学会什么

你要学会不用看懂全部代码，也能通过验收清单检查 AI 开发结果。验收不是感觉一下，而是逐条测试。

为什么这一章重要

AI 协同开发最容易失败的地方，往往不是模型不会写代码，而是人没有把目标、边界、检查点和验收方式定义清楚。本章的作用，是把一个容易凭感觉推进的环节，变成可以重复执行的训练动作。你不需要一开始掌握传统软件工程的全部知识，但你必须能把 AI 的输出限制在自己能审查、能判断、能返工的范围内。

核心概念

  • 验收清单：可执行检查项。
  • 正常流程：用户按预期操作。
  • 异常流程：输入错误、生成失败、重复点击等。
  • 边界情况：空输入、长输入、刷新、多次创建。
  • 页面验收：结构、按钮、文案。
  • 状态验收：待执行、生成中、失败等状态。

核心观点

  1. 非程序员也能验收产品结果。
  2. 验收清单应在施工前准备。
  3. 验收覆盖正常、异常和边界。
  4. 每条要能标记通过/未通过/不确定。
  5. 验收结果应直接转成返工单。

主案例推进

错误示范

这不是验收，因为没有覆盖异常、边界和状态。

期望结果：按钮禁用。

1. 从成功标准转验收项

把“空输入不能提交”改成具体操作和期望结果。

2. 覆盖正常流程

输入任务、生成草案、编辑、确认、列表显示。

3. 覆盖异常流程

生成失败、空输入、重复点击、草案为空。

4. 覆盖边界情况

长输入、连续创建、刷新页面、越界功能。

5. 记录结论

通过、未通过、不确定、本版不要求。

8.1 验收不是感觉，而是证据

很多新手用 AI 写完代码后，会打开页面点几下，然后说：

感觉还行。

或者：

好像哪里不对，但说不上来。

这就是没有验收清单的问题。

验收不是让你变成程序员，也不是要求你读懂所有代码。验收的核心是：把产品结果拆成一条条可以手工检查的证据。

你只需要回答：

  1. 我做了什么操作？
  2. 页面应该出现什么结果？
  3. 实际出现了什么结果？
  4. 这一项通过、失败还是不确定？
  5. 如果失败，如何复现？

这 5 个问题足够让你对 AI 产出形成控制。

8.2 验收清单应该在施工前准备

很多人等 coding agent 做完以后才想怎么验收，这会导致一个问题：你会被最终页面牵着走。

正确做法是：在施工前就把验收清单写好。这样施工单和验收清单会互相约束。

施工前写验收清单有三个好处：

  1. 你能提前发现切片定义不清。
  2. coding agent 知道完成标准。
  3. 返工时有明确依据。

主案例中，如果施工前就写了：

空输入时不能生成草案。

那么 coding agent 做完后，你只要测试这一项。如果它没做到，就不是“感觉不好”，而是明确失败项。

8.3 一条好验收项的 4 个字段

一条验收项建议包含：

前置条件：测试前页面处于什么状态。
操作步骤：用户具体怎么操作。
期望结果：页面应该发生什么。
通过标准：满足什么才算通过。

例如：

验收项：空输入不能生成草案
前置条件：任务创建页已打开，任务输入框为空。
操作步骤：点击“生成草案”按钮。
期望结果：系统不生成草案，并提示用户先输入任务描述，或按钮处于禁用状态。
通过标准：空输入不会进入草案生成流程，也不会新增任务。

这就比“空输入要处理好”清楚得多。

组 1：只说感觉

错误验收：

正确验收：

8.13 读者常见卡点

卡点 1：不会判断问题类型

先不用追求完全准确。你可以初步判断：

  • 合同写了但没做到，多半是实现问题。
  • 合同没写清，导致不知道对不对，多半是产品问题或待确认。
  • 出现本版不做的功能，是越界实现。

卡点 2：不想写复现步骤

没有复现步骤，coding agent 很难稳定修复。复现步骤越清楚，返工越可控。

卡点 3：觉得验收太慢

验收慢一次，返工会快很多。没有验收清单，你可能会反复说“还是不对”，但每次都说不清哪里不对。

卡点 4：页面好看但流程不对

不要被视觉骗了。第一切片优先验收流程、状态、边界，再验收美观。

第 9 章：如何写返工单，判断该返工产品还是返工实现

版本：v0.2 核心训练扩写版
本章定位：核心训练章节

本章你要学会什么

你要学会把“感觉不对”变成 coding agent 能执行的返工任务，并判断问题到底该改产品定义还是改代码。

为什么这一章重要

AI 协同开发最容易失败的地方，往往不是模型不会写代码，而是人没有把目标、边界、检查点和验收方式定义清楚。本章的作用，是把一个容易凭感觉推进的环节，变成可以重复执行的训练动作。你不需要一开始掌握传统软件工程的全部知识，但你必须能把 AI 的输出限制在自己能审查、能判断、能返工的范围内。

核心概念

  • 产品返工：目标、流程、交互、文案需要改。
  • 实现返工：需求明确但代码没做到。
  • 复现步骤：让别人重复看到问题。
  • 当前结果：系统实际表现。
  • 期望结果：你希望的表现。
  • 修改范围：本次允许改哪里。
  • 返工复验：修完后重新检查。

核心观点

  1. 返工不是重新做，而是最小修正。
  2. 产品返工和实现返工要分开。
  3. 不好用不是返工单。
  4. 返工也要写做/不做边界。
  5. 每次返工后必须复验相关项。

主案例推进

模拟问题：确认按钮位置不明显；空输入仍可提交；状态文案显示处理中而不是待执行；coding agent 自行加入员工配置页。分别判断为产品/交互、实现、实现或需求未定义、越界实现。

返工单要避免“二次发散”

返工阶段最容易出现二次发散。原因是你已经看到了一些问题，情绪上会想“干脆一起优化”。但这样会让返工变成新一轮大开发。正确做法是：一个返工单只修验收失败相关问题。

如果你发现了新想法，先写到“下一切片候选”，不要塞进本次返工。

返工单中的范围限制示例

允许修改：
- 任务创建页；
- 草案确认组件；
- 任务列表组件；
- 与上述组件直接相关的本地状态逻辑。

不允许修改：
- 路由结构；
- 全局布局；
- 登录注册；
- 权限相关文件；
- 审批页面；
- 员工配置页面；
- 与第一切片无关的样式系统。

这类范围限制能显著减少 coding agent 顺手重构。

产品返工示例

问题：用户生成草案后，不知道是否还可以编辑。
原因：页面预览没有说明草案字段是可编辑的，也没有编辑态样式。
处理：先修改页面预览和验收标准，再施工。

返工单：

请调整草案确认区交互：
1. 草案字段应以可编辑输入框形式展示；
2. 每个字段旁不需要单独编辑按钮；
3. 确认创建前用户可以修改标题、目标、交付物；
4. 不改任务列表，不新增审批。

实现返工示例

问题：产品合同和验收清单都要求空输入禁用，但实现中按钮仍可点击。
处理：直接实现返工。

返工单：

修复空输入提交问题。
复现步骤：打开页面，不输入内容，点击生成任务草案。
当前结果：按钮可点击并生成空草案。
期望结果：输入为空时按钮禁用，不能触发生成。
只修改任务输入区相关逻辑，不改其他页面。

越界实现处理

如果 coding agent 自行加入了员工配置页，不要说“这个也挺好，先留着”。第一切片阶段，越界内容会干扰验收。你可以选择：

  1. 删除；
  2. 隐藏；
  3. 移到后续分支；
  4. 记录到下一切片候选。

返工话术：

本次第一切片不包含员工配置页。请移除页面入口和相关展示，不要继续实现配置功能。如果相关文件已新增，请在变更说明中列出，并说明是否删除或保留为未引用文件。

返工后复验规则

返工后不要全量乱测，先复验相关项，再做一次核心链路冒烟测试。

1. 复验返工相关验收项；
2. 走一遍正常主流程；
3. 检查是否引入越界功能；
4. 记录是否通过；
5. 如果失败，再写下一张返工单。

返工提示词增强版

你是 coding agent。请只执行下面返工单，不要新增功能，不要顺手优化。
如果你认为需要改动无关文件，必须先说明原因。
返工完成后，请逐条说明复验项是否通过，并列出所有变更文件。

v0.2 核心训练扩写：把“感觉不对”变成可执行返工单

本节扩写第 9 章。目标是让读者学会把验收失败项变成 coding agent 能准确修复的返工任务。

9.1 返工不是重做，而是最小修正

很多新手发现 AI 写出来的东西不对时，会直接说：

不对，重写一下。

或者：

这个页面不好用，优化一下。

这两句话都会让返工失控。

返工的目标不是让 coding agent 重新发挥一次，而是针对已经发现的问题做最小修正。

返工单要回答：

  1. 哪个验收项没通过？
  2. 如何复现？
  3. 当前结果是什么？
  4. 期望结果是什么？
  5. 只允许改哪里？
  6. 不允许顺手改哪里？
  7. 修完后复验哪些项？

如果这些问题没写清，返工很容易引入新问题。

9.2 产品返工和实现返工必须分开

这是第 9 章最重要的判断。

实现返工

实现返工指：产品合同、施工单或验收清单已经写清楚，但 coding agent 没做到。

例子：

验收标准写了：空输入不能生成草案。
实际结果：空输入仍然生成草案。

这就是实现返工。

产品返工

产品返工指：原来的产品定义不清、交互设计不合理、字段设计不完整，需要你重新定义产品规则。

例子：

草案确认按钮应该放在哪里，之前没有定义。现在发现用户不容易看到。

这更接近产品返工。你要先决定按钮位置和交互规则，再让 coding agent 修改。

待确认问题

有些问题暂时不能直接归类。

例子：

风险等级默认是低、中、高，还是只显示是否高风险？

这属于待确认。不能让 coding agent 自己决定。

9.3 主案例问题分类

假设第 8 章验收后发现 4 个问题。

问题 A：确认按钮不明显

当前结果：生成草案后，确认创建按钮在页面底部，用户需要滚动才能看到。
期望结果：确认创建按钮应该位于草案卡片右下角。

分类：产品 / 交互返工。

原因：按钮位置属于交互决策。如果之前页面预览没写清，需要先补充产品定义。

问题 B：空输入仍可提交

当前结果：输入框为空时点击生成草案，系统生成了空草案。
期望结果：空输入时按钮禁用或提示请输入任务描述。

分类：实现返工。

原因：验收清单已明确要求空输入不能生成草案。

问题 C：任务状态显示为“处理中”

当前结果：确认后任务状态显示为处理中。
期望结果：状态应为待执行。

分类：实现返工。

问题 D：多了员工配置页

9.4 三组错误返工 vs 正确返工

组 1：模糊反馈

错误返工：

这个页面不好用，你优化一下。

正确返工：

请只修复确认按钮不明显的问题。

期望结果：确认创建按钮放在草案卡片右下角，并使用主按钮样式。
不允许改动：不要修改任务列表、草案字段、页面路由和其他功能。
复验项：草案生成后能看到确认按钮；点击确认后任务仍能进入列表。

组 2：要求整体重做

错误返工：

这个实现不符合预期，重新做任务创建功能。

正确返工：

请只修复以下两个实现偏差：
1. 空输入时仍可生成草案。
2. 确认后状态显示为“处理中”，应改为“待执行”。

组 3：顺手扩展

错误返工：

顺便把审批功能也加上。

正确返工：

本次返工只修复第一切片问题，不新增审批功能。审批功能放入下一切片计划。

9.16 读者常见卡点

卡点 1：总想让 AI “整体优化”

整体优化通常会引入新问题。返工阶段要克制，只修已发现问题。

卡点 2：不会写期望结果

期望结果来自三个地方：产品合同、施工单、验收清单。如果三者都没写，那就是产品返工，需要先补定义。

卡点 3：返工后忘记复验

返工后不复验，就不知道修复是否真的生效，也不知道有没有引入新问题。

卡点 4：让 coding agent 决定产品规则

不要把“按钮放哪里”“状态叫什么”“风险等级怎么分”这类问题完全丢给 coding agent。它可以建议，但最终要你确认。

v0.3 扩写：把方法固化成自己的开发系统

前面章节解决的是单个切片怎么做。第 10 章要解决的是：如何把这一套方法变成你以后每个项目都能复用的工作流。

10.1 个人 AI 协同开发 SOP

下面是一套适合新手的 12 步 SOP。

第 1 步：写产品想法记录卡

只用 100–200 字写清楚：我想做什么、给谁用、解决什么问题、为什么现在想做。不要一开始写完整方案。

第 2 步：让 GPT 压缩最小闭环

请不要展开完整系统。请基于下面的想法，列出 3 个最小可验证闭环。
每个闭环必须包含：用户起点动作、系统反馈、终点结果、可验收价值。

第 3 步：选择第一切片

用四个维度打分：用户可见价值、实现复杂度、验收难度、后续承接价值。优先选择高价值、低复杂、易验收、能承接后续的切片。

第 4 步：写一页纸产品合同

把第一切片写成产品合同。重点不是完整，而是本版闭环、成功标准、本版不做、待确认项。

第 5 步：让 GPT 审查产品合同

不要让 GPT 扩展功能，而是让它审查模糊点和越界风险。

第 6 步：生成页面预览

只生成页面预览，不写后端、数据库、接口。

第 7 步：审查页面预览

用页面预览审查表检查：路径是否完整、状态是否覆盖、是否越界、是否能转施工。

第 8 步：写施工任务单

施工单必须包含目标、输入材料、输出交付、本次做什么、本次不做什么、验收标准、变更文件清单要求。

第 9 步：交给 coding agent

给 Claude Code / Codex 的指令要明确：

只实现本施工单范围。遇到不确定项先记录，不要自行扩展。完成后列出变更文件、运行方式、已知问题和验收对照。

第 10 步：按验收清单测试

不要凭感觉。逐条记录：通过 / 未通过 / 不确定。

第 11 步：写返工单

返工单只针对未通过项，不要重新做整个切片。

第 12 步：复盘并规划下一切片

复盘四件事：哪些地方偏航了、哪些提示词有效、哪些验收项漏了、下一切片是什么。

10.3 主案例完整沉淀示例

1. 产品合同

AI 员工任务创建与草案确认闭环：用户输入任务描述，系统生成可编辑草案，用户确认后任务进入列表，初始状态为“待执行”。

2. 第一切片

任务创建 → 草案生成 → 草案编辑 → 确认创建 → 列表显示。

3. 页面预览

包含任务创建页、草案确认区、任务列表页、简版详情；审批弹窗作为后续伏笔，不施工。

4. 施工单

只实现第一切片的前端可交互版本，使用 mock 数据，不接真实后端，不做审批、真实执行、权限和长期记忆。

5. 验收清单

  • 空输入不能提交；
  • 输入后能生成草案；
  • 草案可编辑；
  • 确认后任务进入列表；
  • 状态为“待执行”；
  • 不出现越界功能。

6. 返工单示例

只修复空输入仍可提交、状态文案错误两个问题。不要新增页面，不要改动列表布局。

7. 下一切片

高风险任务 → 触发审批弹窗 → 用户同意/拒绝 → 状态更新。

10.4 如何管理提示词资产

很多人每次都重新问 GPT，导致质量不稳定。更好的方式是把有效提示词保存下来，形成自己的提示词资产。

建议至少保存 6 类：压缩模糊需求提示词、产品合同生成提示词、产品合同审查提示词、页面预览提示词、施工单提示词、验收/返工提示词。

每条提示词旁边记录：使用场景、输入材料、输出结果、哪次项目使用过、效果如何、后续改进。

10.6 新手每周训练节奏

第 1 周：只练压缩需求

每天拿一个想法，压缩成产品合同，不写代码。

第 2 周：只练页面预览

把产品合同转成页面预览，重点练状态和用户路径。

第 3 周：只练施工单

把页面预览转成 coding agent 施工单，重点练做/不做边界。

第 4 周：只练验收和返工

模拟或真实跑项目，写验收清单、返工单和复盘。

这样训练 30 天，你不一定成为专业程序员，但会明显提升对 AI 开发过程的控制力。

产品合同

一页纸开发约定，说明第一版为谁解决什么问题，做到什么算成功，哪些明确不做。

页面预览

页面结构、信息、按钮、路径和状态的提前设计。重点是验证流程，不是追求视觉效果。

最小闭环

从用户动作到可见结果的最短完整业务链路。

切片

围绕一个最小闭环形成的可开发、可运行、可验收任务。

纵向切片

从用户入口一路切到结果，包含一点页面、一点状态、一点数据，但链路完整。

横向拆分

按前端、后端、数据库等层拆任务。新手容易反馈太晚。

施工任务单

给 Claude Code / Codex 的单次开发指令，包含目标、范围、约束、验收和汇报要求。

验收清单

一组可执行检查项，用于判断 AI 产出是否符合预期。

产品返工

目标、流程、交互、文案或验收标准不清楚，需要改产品定义。

实现返工

需求已经清楚，但代码没有做到，需要改实现。

mock 数据

假数据或模拟数据，用来在不接真实系统时验证流程。

前端

用户能看到和操作的页面、按钮、表单、弹窗、列表。

后端

支撑前端的服务，通常处理数据、业务逻辑、权限、接口。

接口

前端和后端交换数据的约定。

状态

系统当前处于什么情况，例如空、加载中、失败、待执行、已完成。

空状态

没有数据时页面显示的提示，不应该是空白。

加载态

系统处理中给用户的反馈，例如按钮显示“生成中”。

错误态

操作失败时的反馈，例如“生成失败，请稍后重试”。

边界情况

容易被忽略的特殊输入或操作，如空输入、长输入、重复点击。

复现步骤

让别人能重复看到同一个问题的操作说明。

系统现在实际发生的情况。

期望结果

你希望系统应该发生的情况。

越界功能

本切片明确不做，但 AI 自行加入的功能。

复验

返工后重新检查相关验收项。

复盘

切片结束后总结哪里偏、为什么偏、下次如何减少偏差。

v0.3 扩写：新手友好术语补充

产品合同

产品合同是一页纸的开发约定。它不追求完整，而是说明当前版本要解决什么问题、走完什么闭环、哪些事情不做。

例子：任务创建闭环的产品合同会写明“本版不做真实执行和长期记忆”。

页面预览

页面预览是代码施工前的可视化方案。它说明页面有哪些区块、按钮如何点击、不同状态如何显示。

例子：生成任务草案时，要有初始状态、生成中、生成成功、生成失败。

最小闭环

最小闭环不是最小按钮，而是最小可验证业务链路。

例子：输入任务 → 生成草案 → 确认 → 进入列表，就是一个闭环。

纵向切片

纵向切片是沿着用户路径切一段，从前端页面到状态变化都有一点，目标是让一个功能能跑通。

例子：任务创建切片会包含输入框、生成草案、确认、列表展示，而不是只做数据库表。

横向拆分

横向拆分是按技术层拆，例如先做所有页面，再做所有接口，再做所有数据库。成熟团队可以这样做，但新手用 AI 开发容易反馈太晚。

施工任务单

施工任务单是给 coding agent 的单次开发指令。它必须写清目标、范围、不做项、交付物和验收标准。

验收清单

验收清单是判断结果是否合格的检查表。每条都要能判断通过、失败或不确定。

产品返工

产品返工是因为需求、流程、交互、文案定义不清导致的返工。

例子：按钮放哪里原本没定义，用户觉得不明显，这属于产品或交互返工。

实现返工

实现返工是需求已经写清楚，但代码没有按要求实现。

例子：合同写明空输入不能提交，但页面仍能提交，这属于实现返工。

越界实现

越界实现是 coding agent 做了当前切片不要求的功能。

例子：第一切片只做任务创建，但代码里新增了员工配置页。

mock 数据

mock 数据是假数据，用来先验证页面和流程，不依赖真实后端。

例子：草案生成可以先用固定规则模拟，不必第一版就接真实 AI。

状态

状态是页面或任务当前所处的情况。

例子：任务状态可以是待执行、审批中、执行中、已完成。

复盘

复盘是完成一个切片后回看过程：哪里偏航、哪里有效、下次如何改进。
