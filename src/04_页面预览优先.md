# 第 4 章：如何先做页面预览，而不是一开始就讲后端

> 版本：v0.1 全章初稿  
> 本章定位：基础训练章节

## 本章你要学会什么

你要建立先看页面、再谈实现的习惯。页面预览让新手能审查流程、信息结构、按钮和状态，而不是过早陷入后端、数据库、接口。

## 为什么这一章重要

AI 协同开发最容易失败的地方，往往不是模型不会写代码，而是人没有把目标、边界、检查点和验收方式定义清楚。本章的作用，是把一个容易凭感觉推进的环节，变成可以重复执行的训练动作。你不需要一开始掌握传统软件工程的全部知识，但你必须能把 AI 的输出限制在自己能审查、能判断、能返工的范围内。

## 核心概念

- 页面预览：页面结构和流程的提前设计。
- 信息结构：页面上展示什么、先后顺序是什么。
- 用户路径：用户从进入页面到完成目标的步骤。
- 状态设计：空、加载、错误、成功、禁用、编辑。
- 前端原型：可用于验证流程的低成本材料。

## 核心观点

1. 页面预览是新手最容易审查的材料。
2. 后端和数据库不应抢在流程确认之前。
3. 好不好用首先体现在页面路径上。
4. 页面预览不是视觉设计，而是流程验证。
5. 每个用户可见功能都应该先看预览。

## 主案例推进

主案例页面包括任务创建页、草案确认区、任务列表区、任务详情简版和后续审批弹窗伏笔。第一切片重点只做前三者。

```text
基于产品合同，请帮我设计前后端架构和数据库。
```

问题是：还没确认用户怎么用，就进入技术实现。

## 正确示范

```text
基于产品合同，请不要写后端和数据库。先输出任务创建闭环的页面预览，包括页面区块、按钮、点击路径、空状态、加载态、错误态。
```

## 方法拆解

### 1. 页面标题和目标

每个页面先写目标，例如让用户输入任务并生成草案。

### 2. 页面区块

任务创建页可分顶部说明、输入区、草案区、列表区。

### 3. 按钮和点击结果

每个按钮必须说明点击后发生什么。

### 4. 状态设计

空输入、生成中、失败、成功、草案编辑都要定义。

## 常见误区

### 误区：页面预览等于视觉设计

页面预览重点是流程，不是颜色。

### 误区：mock 页面没意义

mock 页面能提前暴露流程问题。

### 误区：状态可后补

状态缺失会直接导致不好用。

## 页面预览阶段不要急着追求漂亮

新手常犯的一个错误是，把页面预览理解成 UI 设计，开始纠结颜色、圆角、阴影、动效。视觉当然重要，但第一轮页面预览更重要的是：信息有没有放对，路径有没有走通，状态有没有反馈。

你可以先问这几个问题：

- 用户进来第一眼知道这是干什么的吗？
- 用户知道第一步要输入什么吗？
- 主要按钮在哪里？
- 点击按钮后页面会发生什么？
- 失败时用户知道怎么处理吗？
- 没有数据时页面如何引导？

如果这些问题没解决，页面再漂亮也不好用。

## 页面预览的三层

### 第一层：信息层

页面上有哪些信息？例如任务标题、目标、交付物、风险等级、状态。

### 第二层：动作层

用户能做什么？例如生成草案、重新生成、编辑草案、确认创建。

### 第三层：反馈层

用户操作后系统如何反馈？例如 loading、成功提示、错误提示、按钮禁用。

三层缺一不可。很多页面“不好用”，不是因为缺功能，而是缺反馈。

## 主案例页面路径更细示例

```text
1. 用户进入任务创建页；
2. 看到说明文案，知道要输入任务；
3. 输入框为空时，生成按钮禁用；
4. 输入任务后，按钮变为可点击；
5. 点击后按钮显示“生成中……”；
6. 成功后出现草案卡片；
7. 用户编辑标题或交付物；
8. 点击确认创建；
9. 顶部出现成功提示；
10. 新任务出现在列表第一行，状态为待执行。
```

这个路径可以直接变成验收清单。

## 页面预览返工提示词

```text
请审查下面页面预览是否适合新手使用。
重点检查：
1. 用户第一步是否清楚；
2. 每个按钮点击后是否有结果；
3. 是否缺少空状态、加载态、错误态；
4. 是否出现本切片不做的功能；
5. 哪些文案容易让用户误解。
```

# v0.3 扩写：先让新手看得见，再让代码做得深

对非科班新手来说，最容易审查的不是数据库，不是接口，也不是架构图，而是页面。页面不是肤浅的“好不好看”。页面承载了用户路径、信息结构、状态变化和操作反馈。一个系统是否好用，最早往往能从页面预览里看出来。

因此，本书要求：**每个用户可见切片，都先做页面预览，再进入施工。**

## 4.1 页面预览解决什么问题

### 问题一：用户从哪里开始

如果用户打开页面不知道第一步该做什么，后端再强也没用。主案例第一切片中，用户第一步应该非常明确：在任务输入框中描述希望 AI 员工完成的任务。页面上应该有明显输入区和生成草案按钮。

### 问题二：系统反馈是什么

用户点击“生成草案”后，页面应该显示 loading 文案、草案卡片、错误提示或空状态说明？这些都属于页面预览阶段要确认的内容。

### 问题三：用户如何确认

AI 生成草案后，用户不能被迫直接提交。页面应该支持查看草案、编辑草案、取消、确认创建。这体现了本书强调的“人工确认点”。

### 问题四：结果如何承接

确认后任务进入哪里？列表显示哪些字段？状态是什么？用户能否点开详情？这些决定了闭环是否完整。

## 4.2 页面预览不是视觉稿

页面预览的第一目标是验证信息是否完整、操作路径是否顺、状态是否可理解、边界是否覆盖、是否出现越界功能。视觉风格可以先简单，但结构要清楚。

## 4.3 主案例页面预览扩写

### 页面一：任务创建页

页面目标：让用户输入任务描述，并生成可编辑草案。

页面区块：

1. 页面标题区：标题“创建 AI 员工任务”，副标题“描述你希望 AI 员工完成的任务，系统会先生成草案供你确认”。
2. 任务输入区：多行文本框，placeholder 可以是“请帮我整理本周潜在客户名单，并标出需要优先跟进的对象”。
3. 操作按钮区：主按钮“生成任务草案”，次按钮“清空输入”。
4. 草案确认区：初始为空状态；生成后显示草案卡片；字段包括任务标题、任务目标、补充说明；每个字段可编辑；按钮包括确认创建任务、重新生成、取消。
5. 错误提示区：空输入提示、生成失败提示。

状态设计：

| 状态 | 页面表现 |
|---|---|
| 初始状态 | 显示输入框和空的草案提示 |
| 输入中 | 生成按钮可用 |
| 空输入 | 生成按钮禁用或点击后提示 |
| 生成中 | 按钮 loading，输入框可暂时禁用 |
| 生成成功 | 显示草案卡片 |
| 生成失败 | 显示错误提示和重试按钮 |
| 确认成功 | 任务进入列表 |

### 页面二：任务列表页

页面目标：让用户看到已创建任务，并确认新任务进入系统。

页面区块：页面标题、列表区、空状态、任务卡片。第一版可不做分页、高级筛选、批量操作、多人分派和复杂详情页。

### 页面三：任务详情页简版

第一版可以只做简版详情，甚至可以用列表展开代替完整详情页。显示任务标题、任务目标、补充说明、状态、创建时间、返回列表。

### 页面四：审批弹窗伏笔

虽然第一切片不做审批，但可以在页面预览里把它作为后续伏笔标记，而不是施工范围：

```text
高风险审批弹窗：第二切片再做。本章只记录位置和未来触发点，不进入当前施工任务单。
```

这个写法很重要：既不丢掉后续方向，也不让它污染第一切片。

## 4.4 页面预览提示词扩写

```text
请基于下面的一页纸产品合同，输出第一切片的页面预览方案。

本轮只做页面预览，不写后端、数据库、接口、技术架构。

请按以下结构输出：
1. 本切片需要哪些页面或页面区块。
2. 每个页面的目标。
3. 每个页面包含哪些区块。
4. 每个区块展示什么信息。
5. 主要按钮和点击后发生什么。
6. 初始状态、空状态、loading 状态、成功状态、失败状态。
7. 哪些内容属于后续版本，不进入本切片。
8. 页面预览验收清单。

限制：
- 不要新增产品合同之外的功能。
- 不要展开真实 agent 执行。
- 不要设计复杂权限、长期记忆、多员工调度。
- 不确定的地方放入待确认项。

产品合同如下：
{粘贴产品合同}
```

## 4.6 错例与正例：页面预览阶段不要抢跑

错例：

```text
任务创建页使用 React + Zustand + PostgreSQL + FastAPI，后端提供 /api/tasks 接口。
```

这已经进入技术实现。页面预览阶段应该写：

```text
任务创建页包含任务输入区、草案确认区和任务列表入口。点击生成草案后显示可编辑草案；点击确认后任务进入列表。
```

错例：

```text
左侧导航包含员工管理、任务管理、审批中心、知识库、工具市场、系统设置、账单中心。
```

第一切片不需要这些。更好的写法：

```text
第一版只需要任务创建入口和任务列表入口。其他导航项不出现，避免用户误以为本版已支持完整系统。
```

## 4.7 从页面预览到施工单

页面预览确认后，不能直接说“按这个做”。你要把它转成施工任务单。页面预览提供的是内容，施工单要补充施工目标、代码范围、不做项、mock 数据要求、交付物、验收清单、禁止自行扩展。

也就是说，页面预览回答“用户看到什么”，施工单回答“coding agent 这次怎么做、做到哪里停止”。

## 4.8 本章扩写小结

页面预览是新手控制 AI 开发的第一道可视化检查点。它让你在 coding agent 大量改代码之前，先确认用户路径、信息结构和状态反馈。
