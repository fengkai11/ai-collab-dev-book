# 第 7 章：如何给 Claude Code / Codex 写施工任务单

> 版本：v0.2 核心训练扩写版  
> 本章定位：核心训练章节

## 本章你要学会什么

你要学会把产品切片转成 coding agent 能执行的施工任务单。施工单不是 PRD，而是一次清晰的施工命令。

## 为什么这一章重要

AI 协同开发最容易失败的地方，往往不是模型不会写代码，而是人没有把目标、边界、检查点和验收方式定义清楚。本章的作用，是把一个容易凭感觉推进的环节，变成可以重复执行的训练动作。你不需要一开始掌握传统软件工程的全部知识，但你必须能把 AI 的输出限制在自己能审查、能判断、能返工的范围内。

## 核心概念

- 施工任务单：面向 coding agent 的单次开发指令。
- 输入：产品合同、页面预览、切片边界。
- 输出：本次必须交付的页面、状态、数据。
- 约束：不做项和技术限制。
- 验收标准：完成后逐条对照。
- 变更文件清单：说明改了什么。

## 核心观点

1. 施工单只做一个切片。
2. 施工单必须写清不做什么。
3. 施工单必须要求完成后汇报。
4. 施工单越清楚，返工越可控。
5. 不要把完整 PRD 原样丢给 coding agent。

## 主案例推进

主案例施工目标：实现 AI 员工任务创建页的前端静态可交互版本。用户能输入任务、生成草案、编辑草案、确认创建、任务进入列表。使用 mock 数据，不接真实后端。

## 错误示范

```text
请根据前面的文档把 AI 员工系统做出来。
你看哪里不合理就顺便优化。
```

范围巨大，没有验收，没有禁止扩展，还允许无关改动。

## 正确示范

```text
请只实现第一切片：任务创建、草案确认、任务进入列表。
不要实现审批、真实执行、权限、长期记忆。
使用 mock 数据。完成后提供变更文件清单、运行方式、验收对照和已知问题。
```

## 方法拆解

### 1. 写任务名称

名称要小，例如任务创建与草案确认第一切片。

### 2. 写本次目标

用一句话定义可见结果。

### 3. 列输入材料

产品合同、页面预览、切片边界、验收清单。

### 4. 列必须实现

输入框、生成按钮、草案区、确认、列表、状态。

### 5. 写明确不做

审批、真实执行、记忆、权限、后端持久化。

### 6. 要求完成后汇报

变更文件、运行方式、验收结果、已知问题。

## 常见误区

### 误区：把 PRD 直接丢给 coding agent

PRD 太大，施工单要窄。

### 误区：没有要求汇报

没有变更说明，你很难审查。

### 误区：一次施工多个切片

多个切片会让返工难定位。

## 本章小结

## 施工单和普通提示词的区别

普通提示词可以用于讨论，施工单用于执行。讨论时可以开放一点，施工时必须收敛。施工单必须回答 coding agent 最关心的几个问题：

- 我这次到底改什么？
- 我参考哪些材料？
- 哪些文件或页面可能相关？
- 哪些功能不能碰？
- 做完如何证明完成？
- 如果需求不清楚怎么办？

如果这些问题没写清，coding agent 就会用自己的判断补全。

## 施工单里的“不做项”要写得像禁止清单

不要只写“不要发散”。要写具体：

```text
本次不做：
1. 不做真实 AI 执行；
2. 不接工具调用；
3. 不新增审批页面；
4. 不新增员工配置页；
5. 不引入登录注册；
6. 不设计数据库；
7. 不改全局路由；
8. 不重构无关组件。
```

越具体，越安全。

## 施工单里的验收标准要能让 coding agent 自查

不要只写：

```text
功能正常。
```

要写：

```text
1. 空输入时生成按钮禁用；
2. 输入任务后可生成草案；
3. 草案字段可编辑；
4. 点击确认后任务进入列表；
5. 列表状态显示“待执行”；
6. 页面不出现审批、权限、员工配置等入口。
```

这样 coding agent 完成后可以逐条汇报。

## 完成后汇报格式很重要

很多人只让 coding agent 写代码，不要求汇报。结果你不知道它改了哪里，也不知道哪些验收项通过了。建议每次施工单最后都加：

```text
完成后请回复：
1. 本次完成了什么；
2. 新增/修改/删除了哪些文件；
3. 如何运行和查看；
4. 对照验收清单逐条说明是否通过；
5. 已知问题；
6. 是否有任何超范围改动。
```

这能显著降低审查难度。

## 施工前二次检查提示词

在把施工单发给 Codex/Claude Code 前，可以先让 GPT 审查：

```text
请你扮演严格的施工单审查员。
检查下面施工单是否会导致 coding agent 发散。
重点检查：范围是否过大、不做项是否具体、验收是否可执行、是否有顺手优化风险、是否缺少完成后汇报格式。
只输出问题和修改建议。
```

## 施工单版本管理

建议每个切片施工单保存版本：

```text
slice-001-construction-v1.md
slice-001-construction-review.md
slice-001-construction-v2.md
```

不要覆盖旧版本。旧版本能帮助你复盘：到底是哪里没写清导致返工。

# v0.2 核心训练扩写：把切片变成 Coding Agent 能执行的施工单

> 本节扩写第 7 章。目标是让读者能写出“Codex / Claude Code 看了就能开工、做完后你也能验收”的施工任务单。

## 7.1 施工任务单不是 PRD

很多新手会把 PRD、产品想法、技术方案、开发命令混在一起给 coding agent。

例如：

```text
我想做一个 AI 员工系统，支持任务创建、审批、执行、记忆、权限、日志。请你帮我实现。
```

这不是施工单。这只是一个大愿望。

施工单的特点是：

1. 只面向一次施工。
2. 只完成一个切片。
3. 输入材料明确。
4. 输出物明确。
5. 约束明确。
6. 验收标准明确。
7. 完成后必须汇报变更文件、运行方式、已知问题。

你可以把施工单理解成：给一个能力很强但不了解你全部意图的施工队下达的“本次只干这些活”的书面命令。

## 7.2 一张合格施工单的 9 个字段

### 字段 1：任务标题

标题要表达当前切片，不要写“开发系统”。

推荐：

```text
实现任务创建 → 草案确认 → 入列表前端切片
```

不推荐：

```text
开发 AI 员工系统
```

### 字段 2：任务目标

用 2–3 句话说明本次施工的终点。

### 字段 3：输入材料

告诉 coding agent 它应该依据哪些材料工作。

例如：产品合同、页面预览、切片边界、验收清单。

### 字段 4：实现范围

列出要做的内容。

### 字段 5：明确不做

这是防止发散的关键。

### 字段 6：技术约束

例如：使用 mock 数据、不接真实后端、不引入新框架、不改无关页面。

### 字段 7：验收标准

每条都要能手工测试。

### 字段 8：交付要求

要求 coding agent 完成后汇报：

- 改了哪些文件
- 如何运行
- 如何验证
- 已知问题
- 哪些验收项已通过

### 字段 9：异常处理

如果发现材料冲突或范围不清，应该先列出问题，而不是自行扩展。

## 7.3 主案例施工单 v1：不合格版本

```text
请根据前面的文档实现 AI 员工系统的任务功能。
```

问题非常多：

- “前面的文档”不明确。
- “任务功能”范围不明确。
- 没有做 / 不做边界。
- 没有说明 mock 还是后端。
- 没有验收标准。
- 没有要求输出变更说明。

这种施工单很容易导致 coding agent 自行发挥。它可能新建一堆页面，也可能设计数据库，还可能加入权限和审批。最后你会觉得“它写了很多，但不是我要的”。

## 7.4 主案例施工单 v2：合格版本

```text
# 施工任务单：实现任务创建 → 草案确认 → 入列表前端切片

## 1. 任务目标

请实现 AI 员工任务系统的第一切片：用户输入任务描述，系统生成一个可编辑的任务草案；用户确认后，任务进入任务列表，初始状态显示为“待执行”。

本次只实现前端可交互版本，使用 mock 草案生成和前端本地状态，不接真实后端。

## 2. 输入材料

请依据以下材料施工：
1. 一页纸产品合同：任务创建与确认闭环。
2. 页面预览：任务创建页、草案确认区、任务列表区。
3. 切片边界：只做任务创建、草案确认、任务入列表。
4. 验收标准：见第 6 节。

## 3. 实现范围

请实现：
1. 任务描述输入框。
2. “生成草案”按钮。
3. 空输入时按钮禁用或提交时提示。
4. 点击生成草案后展示加载态。
5. mock 生成任务草案。
6. 草案卡片展示字段：任务标题、任务目标、预期产出、风险等级。
7. 草案字段可编辑。
8. “确认创建”按钮。
9. 确认后任务进入列表。
10. 列表显示任务标题、状态、创建时间。
11. 初始状态为“待执行”。

## 4. 明确不做

请不要实现：
1. 真实 agent 执行。
2. 真实后端接口。
3. 数据库持久化。
4. 高风险审批。
5. 多员工调度。
6. 长期记忆。
7. 工具调用。
8. 权限系统。
9. 通知系统。
10. 部署配置。

## 5. 技术约束

1. 优先在现有项目结构内实现，不要大规模重构。
2. 不要引入新的大型框架，除非项目已使用。
3. mock 数据应集中放置，便于后续替换为真实接口。
4. 不要改动与本切片无关的页面和模块。
5. 如果发现现有代码结构与任务冲突，请先在完成说明中列出，不要自行扩大改造范围。

## 6. 验收标准

1. 页面存在任务描述输入框。
2. 空输入时不能成功生成草案。
3. 输入任务后点击“生成草案”，能看到加载态。
4. 加载结束后出现草案卡片。
5. 草案字段可以编辑。
6. 点击“确认创建”后，任务进入列表。
7. 列表中任务状态为“待执行”。
8. 页面没有出现审批、执行、员工配置、权限等本切片之外功能。

## 7. 完成后请汇报

请在完成后输出：
1. 变更文件清单。
2. 如何运行项目。
3. 如何手工验证每条验收标准。
4. 已知问题。
5. 哪些内容是 mock，后续如何替换。
```

这就是一张可以给 Codex / Claude Code 的施工单。

## 7.5 三组错误施工单 vs 正确施工单

### 组 1：范围过大

错误施工单：

```text
请实现 AI 员工系统，包括任务、审批、执行、记忆和权限。
```

正确施工单：

```text
请只实现第一切片：任务创建、草案确认、任务进入列表。不要实现审批、执行、记忆和权限。
```

### 组 2：没有交付要求

错误施工单：

```text
做完告诉我。
```

正确施工单：

```text
完成后请提供变更文件清单、运行方式、验收项完成情况、已知问题和 mock 内容说明。
```

### 组 3：允许顺手优化

错误施工单：

```text
你看哪里不合理就顺手优化一下。
```

正确施工单：

```text
不要改动与本切片无关的页面、路由、状态管理和样式体系。如发现问题，请在完成说明中列为建议，不要直接修改。
```

## 7.6 字段解释：单页施工任务单模板

### 任务标题

标题用于让 coding agent 和你自己都记住本次施工边界。不要用“第一阶段开发”这种模糊标题。

### 背景

背景只写必要内容。过多背景会让 agent 自行扩展。

### 当前切片

这是施工单的核心锚点。最好复制第 5 章的一句话定义。

### 输入材料

输入材料越明确，agent 越不容易翻旧账或乱引用。

### 实现范围

写成编号列表。每一条最好对应页面上的一个可见结果或状态变化。

### 不做范围

不做范围要具体，越具体越好。

### 技术约束

新手不一定懂技术细节，但可以写过程约束，例如：

```text
不要大规模重构。
不要引入无关依赖。
不要修改无关文件。
```

### 验收标准

施工单里的验收标准应该和第 8 章验收清单一致。不要施工时一套标准，验收时另一套标准。

### 完成汇报

这个字段很重要。因为你不一定看得懂所有代码，但你可以看懂 agent 的变更说明和验证说明。

## 7.10 主案例：从切片定义到施工单的转换过程

### 输入材料 1：切片定义

```text
用户输入任务描述，系统生成可编辑任务草案，用户确认后任务进入列表并显示为待执行。
```

### 输入材料 2：页面范围

```text
任务创建页、草案确认区、任务列表区。
```

### 输入材料 3：不做边界

```text
不做真实 agent、后端、数据库、审批、执行、权限、记忆。
```

### 转换成施工项

| 切片元素 | 施工项 |
|---|---|
| 用户输入任务描述 | 实现任务描述输入框 |
| 生成草案 | 实现生成草案按钮和 mock 逻辑 |
| 草案可编辑 | 实现草案卡片和字段编辑 |
| 用户确认 | 实现确认创建按钮 |
| 进入列表 | 实现任务列表状态更新 |
| 状态待执行 | 列表状态字段显示“待执行” |

这张转换表能帮你发现：施工单不是凭空写的，它来自切片定义。

## 7.11 练习扩写与参考答案

### 练习 1：识别不合格施工单

施工单：

```text
请把 AI 员工系统第一版做出来，页面好看一点，功能完整一点，缺的你自己补。
```

参考答案：

问题：

```text
1. “第一版”范围不清。
2. “好看一点”不可验收。
3. “功能完整一点”会导致发散。
4. “缺的你自己补”允许脑补。
5. 没有不做范围。
6. 没有验收标准。
```

### 练习 2：补全施工单字段

缺失施工单：

```text
请实现任务创建页面。
```

参考补全：

```text
任务目标：实现任务创建 → 草案确认 → 入列表切片。
实现范围：输入框、生成草案、草案编辑、确认创建、任务列表。
不做范围：真实 agent、审批、执行、后端、数据库、权限。
验收标准：空输入不能提交；输入后生成草案；草案可编辑；确认后入列表；状态为待执行。
完成汇报：变更文件、运行方式、验收结果、已知问题。
```

### 练习 3：为主案例写施工单

可直接使用 7.4 的合格版本。

### 练习 4：为自己的项目写施工单

示范：外贸询盘报价辅助工具。

```text
任务目标：用户粘贴客户询盘，系统生成可编辑报价草案。
实现范围：询盘输入、生成报价草案、草案编辑、确认保存。
不做范围：真实邮件发送、ERP 对接、库存校验、复杂价格策略。
验收标准：空询盘不能生成；输入询盘后出现报价草案；报价字段可编辑；确认后进入报价记录列表。
```

### 练习 5：压缩施工范围

原施工单：

```text
实现外贸获客系统，包括客户搜索、评分、邮件发送、跟进、CRM。
```

压缩后：

```text
只实现第一切片：用户输入目标国家和产品关键词，系统生成 mock 客户列表，用户可以标记是否值得跟进。不要做邮件发送、自动跟进、CRM 和真实搜索。
```

### 练习 6：让 GPT 审查施工单

可复制提示词：

```text
请审查下面施工任务单是否适合交给 Codex / Claude Code 执行。
重点检查：范围是否过大、是否缺少不做项、是否有不可验收标准、是否允许 coding agent 脑补、是否缺少完成汇报要求。
请输出：问题清单、修改建议、修订版施工单。

施工任务单：
{粘贴施工单}
```

## 7.12 读者常见卡点

### 卡点 1：不知道技术约束怎么写

你不懂代码也可以写过程约束：不大规模重构、不引入无关依赖、不改无关文件、mock 数据集中放置。这些约束足够有价值。

### 卡点 2：施工单越写越像 PRD

施工单不是描述未来系统，而是描述本次要改什么。凡是本次不做的，都移出施工单正文，放到后续计划。

### 卡点 3：不知道怎么要求 agent 汇报

直接固定要求 5 件事：变更文件、运行方式、验收结果、已知问题、mock 说明。

### 卡点 4：怕不让 agent 发挥会影响质量

施工阶段不需要自由发挥。你可以让它在完成说明中提出建议，但不要让它直接顺手改。

## 7.14 本章小结补强

施工单是 AI 协同开发从“讨论”进入“实现”的分界线。

记住一句话：

```text
一张施工单，只做一个切片；一条验收标准，对应一个可检查结果。
```

只要你能稳定写出施工单，coding agent 的能力就更容易被你驾驭，而不是反过来让它带着项目到处跑。
