# 第 3 章：如何把模糊想法压缩成一页纸产品合同

> 版本：v0.1 全章初稿  
> 本章定位：基础训练章节

## 本章你要学会什么

你要学会写一页纸产品合同。它不是完整 PRD，而是开发前的最低约定，用来锁定用户、问题、本版闭环、成功标准、不做项和待确认项。

## 为什么这一章重要

AI 协同开发最容易失败的地方，往往不是模型不会写代码，而是人没有把目标、边界、检查点和验收方式定义清楚。本章的作用，是把一个容易凭感觉推进的环节，变成可以重复执行的训练动作。你不需要一开始掌握传统软件工程的全部知识，但你必须能把 AI 的输出限制在自己能审查、能判断、能返工的范围内。

## 核心概念

- 产品合同：一页纸开发约定。
- 目标用户：第一版最优先服务的人。
- 核心问题：用户真实阻碍。
- 本版闭环：动作到结果。
- 成功标准：可以手工检查的标准。
- 本版不做：防止 AI 发散。
- 待确认项：防止 AI 脑补。

## 核心观点

1. 产品合同的价值不是完整，而是可判断。
2. 合同要用业务语言，不要堆技术名词。
3. 成功标准必须可验收。
4. 不做项和做项同样重要。
5. 待确认项要显性列出。

## 主案例推进

主案例产品合同锁定：AI 员工任务创建与确认闭环。用户输入任务，系统生成草案，用户编辑确认后，任务进入列表并显示待执行。本版不做真实执行、记忆、审批、权限。

## 错误示范

```text
我要做一个强大的 AI 员工系统，具备任务、记忆、工具、权限、审批、复盘等能力，体验要好，系统要稳定。
```

这不是产品合同，而是愿景。它没有第一版闭环，也没有可验收标准。

## 正确示范

```text
第一版只做：用户输入任务 → 系统生成可编辑草案 → 用户确认 → 任务进入列表。成功标准包括空输入不能提交、草案可编辑、确认后列表出现任务。本版不做真实执行、审批、记忆和权限。
```

## 方法拆解

### 1. 功能名称要小

不要写 AI 员工系统，写 AI 员工任务创建与确认闭环。

### 2. 问题写用户语言

不要写构建任务调度架构，写用户不知道 AI 是否理解任务。

### 3. 成功标准可验收

把体验好改成用户 3 分钟内能创建任务。

### 4. 不做项防扩散

不做真实执行、工具调用、长期记忆、复杂权限。

## 常见误区

### 误区：合同写成愿景

愿景可以有，但产品合同要约束第一版。

### 误区：不写不做项

不做项是防止 AI 扩张的关键。

## 产品合同不是为了限制想象力

很多人会担心：只写一页纸，会不会把产品想小了？答案是不会。产品合同限制的不是长期想象力，而是第一版施工范围。你可以有很大的愿景，但第一版必须小到可验证。

一个成熟的做法是把内容分成两层：

```text
长期愿景：
AI 员工能像真实员工一样承担任务、调用工具、总结经验。

第一版合同：
只做任务创建与草案确认闭环。
```

这样既保留了方向，又不会让 coding agent 一开始就冲向完整系统。

## 成功标准改写训练

下面是一些常见虚标准及改写方式：

| 虚标准 | 可验收改写 |
|---|---|
| 系统要好用 | 用户 3 分钟内能完成第一条任务创建 |
| 页面要高级 | 页面包含清晰标题、输入区、草案区、列表区，主要按钮可见 |
| AI 要智能 | 草案至少包含标题、目标、交付物、风险等级 |
| 系统要稳定 | 连续创建 5 条任务不报错 |
| 流程要顺 | 用户从输入到确认不超过 4 个主要动作 |

你会发现，可验收标准往往更朴素，但更能指导开发。

## 待确认项的价值

待确认项不是“没想清楚”的羞耻记录，而是防止 AI 脑补的保险箱。例如你暂时不知道是否支持附件，不要让 AI 自己决定。写成：

```text
待确认：第一版是否支持附件上传？
风险：如果 AI 自行实现附件，会引入文件存储和安全问题。
默认处理：第一版不支持附件，只保留后续扩展位。
```

这种写法能直接降低范围失控风险。

## 产品合同二次审查提示词

```text
请把下面产品合同改写得更适合新手 AI 协同开发。
要求：
1. 缩小功能名称；
2. 把虚的成功标准改成可验收；
3. 补充本版不做项；
4. 把不确定内容列为待确认项；
5. 不要加入技术架构。
```

# v0.3 扩写：产品合同是开发前的最低约定

很多新手不喜欢写产品合同，觉得这是“文档工作”，不如直接让 AI 写页面或写代码。但在 AI 协同开发里，产品合同不是传统意义上的厚 PRD，而是一张很短的“开发约束纸”。

它的作用不是证明你想得多完整，而是回答三个问题：

1. 这次到底要解决谁的什么问题？
2. 这一版用户要走完哪条流程？
3. 哪些事情明确不做？

只要这三个问题没有说清楚，AI 就会替你做决定。

## 3.1 为什么叫“产品合同”

“合同”这个词很重要。它意味着这不是随便写写的想法，而是你和 AI、你和 coding agent、你和未来自己的最低约定。产品合同要做到：后续页面预览必须依据它；后续施工任务单必须依据它；后续验收清单必须依据它；后续返工时也要回到它。

如果产品合同里没有写“本版不做审批”，coding agent 做出审批入口，你就很难说它错了。因为你没有提前约束。如果产品合同里写了“本版不做审批”，那这就是越界实现，可以要求删除或隔离。

## 3.2 产品合同和 PRD 的区别

| 对比项 | 一页纸产品合同 | 传统 PRD |
|---|---|---|
| 目标 | 锁定当前切片 | 描述完整产品 |
| 篇幅 | 1 页左右 | 多页甚至几十页 |
| 读者 | 自己、GPT、coding agent | 产品、设计、研发、测试等团队 |
| 重点 | 用户、流程、边界、验收 | 功能、交互、规则、数据、版本等 |
| 适合阶段 | AI 协同开发早期 | 团队协作和成熟产品阶段 |

本书不是反对 PRD，而是告诉新手：在第一切片之前，不要急着写厚 PRD。先写一页纸产品合同，让范围可控。

## 3.3 一份合格产品合同的 8 个字段

### 字段 1：功能名称

差的写法：

```text
AI 员工系统
```

好的写法：

```text
AI 员工任务创建与草案确认闭环
```

区别在于，后者天然限制了范围。

### 字段 2：目标用户

写清楚谁使用，不要写“所有用户”。主案例中，第一版目标用户是任务发起人 / 管理者。这个人希望把一个任务交给 AI 员工，并确认任务已经被系统记录。暂时不是 AI 员工管理员、团队成员、审计人员或系统运维人员。

### 字段 3：核心问题

不要写“提高效率”这种空话，要写具体卡点。

差的写法：

```text
帮助用户更高效地使用 AI 员工。
```

好的写法：

```text
用户有任务想交给 AI，但不知道如何把任务描述变成一条可确认、可追踪的系统任务。
```

### 字段 4：本版闭环

写成链路：起点 → 系统反馈 → 用户确认 → 终点。

```text
用户输入任务描述 → 系统生成任务草案 → 用户编辑并确认 → 任务进入列表，状态为“待执行”。
```

### 字段 5：成功标准

每条都要能验收。差的写法是“页面体验好，任务创建方便”。好的写法是：

```text
1. 空输入时不能生成草案。
2. 输入任务后能生成包含标题、目标、补充信息的草案。
3. 草案内容可以编辑。
4. 点击确认后，任务进入列表。
5. 列表中显示任务标题、创建时间、状态“待执行”。
```

### 字段 6：本版做什么

明确范围：任务输入框、生成草案按钮、草案展示和编辑、确认创建任务、任务列表展示、基础错误提示。

### 字段 7：本版不做什么

这是产品合同里最容易被忽视、但最关键的字段。

```text
- 不接真实 agent 执行
- 不做真实工具调用
- 不做高风险审批
- 不做长期记忆
- 不做多员工调度
- 不做复杂权限
- 不做数据库持久化，第一轮可用 mock 或本地状态
```

### 字段 8：待确认项

不确定的内容不要让 AI 脑补，先放这里。

```text
- 草案是否需要风险等级？
- 任务类型是否需要枚举？
- 是否支持附件？
- 任务列表是否需要筛选？
```

待确认项不是阻碍开发，而是防止模型自作主张。

## 3.4 主案例产品合同扩写示例

```markdown
# 一页纸产品合同：AI 员工任务创建与草案确认闭环

## 1. 功能名称
AI 员工任务创建与草案确认闭环。

## 2. 目标用户
任务发起人 / 管理者。用户希望把一个任务交给 AI 员工处理，但在任务正式进入系统前，需要先看到一份可编辑的任务草案。

## 3. 核心问题
用户直接输入自然语言任务时，常常描述不完整、不结构化，也不知道任务是否已经被系统记录。本功能要帮助用户把模糊任务描述转成一条可确认、可追踪的任务记录。

## 4. 本版闭环
用户输入任务描述 → 系统生成任务草案 → 用户编辑草案 → 用户确认创建 → 任务进入列表，初始状态为“待执行”。

## 5. 本版做什么
- 提供任务描述输入框。
- 提供“生成草案”按钮。
- 显示任务草案，包括任务标题、任务目标、补充说明。
- 草案字段可编辑。
- 提供“确认创建任务”按钮。
- 确认后任务进入列表。
- 列表显示标题、创建时间、状态。
- 处理空输入和生成失败提示。

## 6. 本版不做什么
- 不执行真实任务。
- 不接真实 AI agent。
- 不调用外部工具。
- 不做审批流。
- 不做多员工分配。
- 不做长期记忆。
- 不做复杂权限。
- 不做数据库持久化。

## 7. 成功标准
- 空输入时不能点击生成草案，或点击后明确提示用户输入任务描述。
- 输入有效任务后，可以生成草案。
- 草案字段可以编辑。
- 点击确认后，任务列表新增一条任务。
- 新任务状态显示为“待执行”。
- 页面不出现本版不做范围内的入口，例如员工配置、权限配置、计费模块。

## 8. 待确认项
- 是否在草案中显示风险等级？第一版暂不显示。
- 是否需要任务类型？第一版暂不需要。
- 是否支持附件？第一版不支持。
- 页面刷新后是否保留数据？第一版不要求。
```

## 3.5 产品合同常见错误

1. **目标用户太宽。**“所有想使用 AI 员工的人”会导致功能扩张。第一版要具体到一个角色。
2. **成功标准不可检查。**“让用户体验丝滑”不是验收项。要改成可观察行为，例如“最多 2 次点击完成任务创建”。
3. **本版不做为空。**不写不做项，等于默认 AI 可以自由扩展。
4. **技术实现抢跑。**产品合同阶段不需要写 Redis、PostgreSQL、微服务、LangGraph 或向量数据库。
5. **待确认项被隐藏。**不确定就显性列出，等真正需要时再决策。

## 3.6 让 GPT 审查产品合同的提示词扩写

```text
你现在是一名 AI 协同开发教练，请审查下面这份一页纸产品合同。

审查目标：不是帮我扩展功能，而是帮我发现模糊点、越界风险和不可验收表达。

请按以下结构输出：
1. 这份合同中已经清楚的部分。
2. 可能导致 GPT 或 coding agent 脑补的部分。
3. 成功标准中不可验收或太虚的表达。
4. 本版不做项是否足够清楚。
5. 建议补充的待确认项。
6. 修改后的更收敛版本。

限制：
- 不要新增完整系统设计。
- 不要写数据库、接口、技术架构。
- 不要把后续版本功能加入本版范围。

下面是产品合同：
{粘贴产品合同}
```

## 3.7 产品合同到下一步的连接

产品合同不是写完就结束。它会继续变成页面预览需求、切片定义、施工任务单、验收清单和返工单。产品合同越清楚，后面的每一步越稳。

## 3.8 本章扩写小结

一页纸产品合同不是为了显得专业，而是为了让你在 AI 面前有边界。它告诉 GPT：不要替我扩展完整系统；它告诉 coding agent：这次只施工这个切片；它也告诉未来的你：验收时不要被漂亮但越界的功能带偏。
