# 第 5 章：如何识别“最小闭环”，并拆出第一个切片

> 版本：v0.2 核心训练扩写版  
> 本章定位：核心训练章节

## 本章你要学会什么

你要掌握从大系统想法中找出第一条最值得打通的小闭环。最小闭环不是最小功能，而是最小可验证业务链路。

## 为什么这一章重要

AI 协同开发最容易失败的地方，往往不是模型不会写代码，而是人没有把目标、边界、检查点和验收方式定义清楚。本章的作用，是把一个容易凭感觉推进的环节，变成可以重复执行的训练动作。你不需要一开始掌握传统软件工程的全部知识，但你必须能把 AI 的输出限制在自己能审查、能判断、能返工的范围内。

## 核心概念

- 最小闭环：起点、过程、终点都清楚的小业务链路。
- 第一切片：准备交给 coding agent 的第一个可运行闭环。
- 起点动作：用户首先做什么。
- 终点结果：用户最终看到什么。
- 人工确认点：AI 早期开发的重要安全带。
- 切片边界：做什么、不做什么。

## 核心观点

1. 最小闭环不是最小按钮，而是最小业务链路。
2. 第一切片优先选择用户看得见价值的链路。
3. 起点和终点不清，切片就不可控。
4. 第一切片不追求自动化最高，而追求验证方向最快。
5. 人工确认不是落后，而是防止 AI 误执行。

## 主案例推进

完整 AI 员工系统包含任务、审批、执行、记忆、工具权限、复盘。但第一切片选：用户输入任务 → AI 生成任务草案 → 用户编辑/确认 → 任务进入列表 → 显示待执行状态。

## 错误示范

```text
先实现完整角色系统、工具权限、任务调度和长期记忆。
```

这不可见、不可快速验收，而且复杂依赖太多。

## 正确示范

```text
先实现任务创建小闭环：输入任务、生成草案、编辑确认、进入列表。草案生成和数据保存都可以先 mock。
```

## 方法拆解

### 1. 写出完整想法

先允许自己写大，但不要直接施工。

### 2. 找用户最早动作

用户第一次打开系统最想做什么？主案例是交代任务。

### 3. 找可见结果

用户交代任务后，至少要看到系统理解出的任务草案和任务列表。

### 4. 加入人工确认

AI 生成草案后先让用户确认，避免误解后直接执行。

### 5. 定义终点

确认后任务进入列表，状态为待执行。

### 6. 写边界

做输入、草案、确认、列表；不做执行、工具、记忆、审批、权限。

## 和 GPT 的对话演示


## 常见误区

### 误区：最小闭环等于最小功能

一个输入框很小，但不是闭环。

### 误区：第一切片必须接真实 AI

可以先 mock，先验证流程。

早期人工确认是安全带。

## 本章小结

最小闭环是大系统落地的第一道闸门。先找到用户第一动作和可见结果，再变成第一切片。

## 深入训练：用“四问法”逼出最小闭环

当你面对一个大想法时，可以连续问四个问题。

### 第一问：用户第一次来，最想完成什么动作？

不要回答“使用系统”。要回答具体动作。主案例中是“创建一条 AI 员工任务”。

### 第二问：用户完成这个动作后，必须看到什么结果才觉得有价值？

主案例中不是“AI 完成任务”，而是“系统生成了可确认的任务草案，并把确认后的任务放入列表”。这是一个更小、更可控的结果。

### 第三问：哪些复杂能力可以先假装存在？

主案例中，真实 AI 执行可以先不做，真实模型生成草案也可以先 mock，长期记忆可以先不做，审批可以先放后续。

### 第四问：如果只做这条链路，用户是否能判断方向对不对？

如果答案是能，这就是好第一切片。如果答案是不能，说明切片可能太偏基础设施。

## 主案例第一切片详细边界

### 必须做

```text
1. 任务输入框；
2. 生成任务草案按钮；
3. 生成中状态；
4. 草案展示卡片；
5. 草案字段可编辑；
6. 确认创建按钮；
7. 任务列表；
8. 任务初始状态“待执行”。
```

### 可以简化

```text
1. 草案生成可以用 mock 规则；
2. 任务数据可以只存在前端状态；
3. 风险等级可以先用低/中/高三档；
4. 任务详情可以先用展开区域，不做独立页面。
```

### 明确不做

```text
1. 不做真实任务执行；
2. 不接工具调用；
3. 不做长期记忆；
4. 不做多员工调度；
5. 不做复杂权限；
6. 不做真实审批流；
7. 不做消息通知；
8. 不做后端持久化。
```

### coding agent 容易越界的地方

```text
1. 自行创建员工配置页面；
2. 自行加入审批中心；
3. 自行设计权限模型；
4. 自行接入真实 LLM API；
5. 自行设计数据库表；
6. 自行增加登录注册。
```

这些内容不是永远不做，而是不属于第一切片。

## 切片评分表案例

| 候选切片 | 用户价值 | 可见性 | 复杂度 | 验收难度 | 是否第一切片 |
|---|---:|---:|---:|---:|---|
| 任务创建与草案确认 | 5 | 5 | 2 | 2 | 是 |
| 高风险审批 | 4 | 4 | 3 | 3 | 第二切片 |
| 执行结果展示 | 4 | 4 | 4 | 4 | 第三切片 |
| 员工配置 | 3 | 3 | 4 | 3 | 暂后 |
| 长期记忆复盘 | 3 | 2 | 5 | 5 | 暂后 |

评分不是为了精确，而是为了让你显性比较。不要凭感觉选“看起来最专业”的切片。

## 读者常见错误拆法

### 错误拆法 1：先做基础能力

```text
先搭好 agent 框架、记忆系统、权限系统，再做任务创建。
```

问题是基础能力无法被普通用户直接验证。你会花很多时间做看不见的东西。

### 错误拆法 2：先做最炫能力

```text
先让 AI 自动执行任务，展示智能效果。
```

问题是依赖太多，错误来源太复杂。到底是任务理解错了、工具调用错了、权限错了，还是执行逻辑错了，很难判断。

### 错误拆法 3：先做配置中心

```text
先让用户配置员工职责、技能、工具权限。
```

问题是没有真实任务时，配置项很容易拍脑袋。

格式：


主案例填法：

```text

```


```text

```

# v0.2 核心训练扩写：把“大想法”压成第一条能跑通的链路

> 本节是对第 5 章的扩写。目的不是多讲概念，而是把“识别最小闭环”训练成一套可以反复使用的动作。

## 5.1 先纠正一个常见误解：最小闭环不是“最小功能”

很多新手听到“最小闭环”，第一反应是：那我是不是只做一个按钮？只做一个输入框？只做一个页面？

这就是第一个误解。

最小闭环不是把功能拆到最小，而是把**业务链路拆到最短**。

一个按钮本身不构成闭环。一个输入框也不构成闭环。一个页面也不一定构成闭环。闭环至少要回答三个问题：

1. 用户从哪里开始？
2. 用户中间做了什么关键动作？
3. 用户最后看到了什么可判断的结果？

例如，在 AI 员工任务系统里，“做一个任务输入框”不是闭环。因为用户输入以后，没有看到系统怎么理解任务，也没有看到任务是否被创建。

更好的闭环是：

```text
用户输入任务 → 系统生成任务草案 → 用户确认 → 任务进入列表 → 状态显示为待执行
```

这条链路虽然简单，但已经能回答一个核心问题：用户能不能把一个任务稳定交给 AI 员工系统。

只要这个问题被验证，后续审批、执行、记忆、工具调用才有意义。反过来，如果这个最基本的交付任务动作都不好用，你提前做再复杂的权限系统、记忆系统、调度系统，都会变成“看起来完整，但核心体验不成立”。

## 5.2 好闭环的 6 个判断标准

判断一个闭环能不能作为第一切片，可以用下面 6 个标准。

### 标准 1：有明确起点

起点必须是用户看得懂、做得出来的动作。

不好的起点：

```text
系统初始化 agent 能力。
```

这个起点对用户不可见，也不容易验证。

好的起点：

```text
用户在任务输入框里输入一句自然语言任务。
```

这个起点清楚、可操作、可测试。

### 标准 2：有明确终点

终点必须是一个用户能看见的结果。

不好的终点：

```text
系统完成任务调度。
```

调度是否完成，新手很难直接判断。

好的终点：

```text
任务出现在任务列表中，状态显示为“待执行”。
```

这个结果可见、可截图、可验收。

### 标准 3：中间路径短

第一切片不要经过太多系统模块。路径越长，问题越难定位。

不好的路径：

```text
输入任务 → 匹配员工 → 查询记忆 → 判断权限 → 调用工具 → 执行任务 → 汇总结果 → 写复盘
```

这个链路看起来完整，但对第一轮开发太长。

好的路径：

```text
输入任务 → 生成草案 → 人工确认 → 入列表
```

第一轮先验证“任务能否被正确创建”。

### 标准 4：能 mock

第一切片最好可以用 mock 数据跑起来。

这不是偷懒，而是降低依赖。因为早期真正要验证的是页面流程、状态变化、用户理解，而不是复杂模型能力。

主案例中，任务草案可以先用规则或固定 mock：

```text
用户输入：帮我整理本周客户开发情况
系统草案：
- 任务标题：整理本周客户开发情况
- 任务目标：汇总本周客户开发进展
- 预期产出：一份简要总结
- 风险等级：低
```

即使这个草案不是由真实 agent 生成，也能先验证草案展示、编辑、确认、入列表这一整条体验。

### 标准 5：能验收

一个好切片必须能写出验收标准。

如果你写不出验收标准，说明这个切片还不够清楚。

例如：

```text
成功标准：用户输入任务后，点击“生成草案”，页面出现可编辑草案；点击“确认创建”，任务进入列表，状态为“待执行”。
```

这就是可验收的表达。

不好的表达是：

```text
系统要智能地理解用户任务。
```

“智能”很难验收。“理解”也容易变成主观感觉。

### 标准 6：后续能自然接下一切片

第一切片不是孤立的，它要给第二切片留下接口。

主案例的第一切片结束于“任务进入列表，状态为待执行”。这正好可以接第二切片：

```text
任务风险判断 → 高风险进入审批 → 用户批准或拒绝 → 状态更新
```

如果第一切片的终点设计得好，后续切片就像接积木一样自然。

## 5.3 主案例第一轮：从完整系统到候选闭环

我们先把完整想法写出来：

```text
我想做一个 AI 员工系统。它有员工角色、职责、记忆、工具权限、任务调度、审批、执行、复盘。管理者可以给 AI 员工分配任务，AI 员工自主执行，并在高风险操作前请求人工审批。
```

这个想法很大。现在不要急着让 GPT 写完整 PRD。先列候选闭环。

### 候选闭环 A：任务创建闭环

```text
用户输入任务 → 系统生成草案 → 用户确认 → 任务进入列表
```

价值：用户能把任务交给系统。  
可见性：高。  
复杂度：低。  
是否可 mock：是。  
是否适合第一切片：非常适合。

### 候选闭环 B：审批闭环

```text
系统识别高风险任务 → 进入审批队列 → 用户同意或拒绝 → 更新任务状态
```

价值：控制风险。  
可见性：高。  
复杂度：中。  
是否可 mock：是。  
是否适合第一切片：不如 A，因为它依赖任务已经存在。

### 候选闭环 C：执行结果闭环

```text
任务执行 → 生成结果 → 用户查看 → 标记满意或需要返工
```

价值：接近最终业务价值。  
可见性：高。  
复杂度：中高。  
是否可 mock：部分可以。  
是否适合第一切片：不适合第一轮，因为真实执行依赖太多。

### 候选闭环 D：员工配置闭环

```text
用户创建 AI 员工 → 设置职责、工具权限、风险规则 → 保存配置
```

价值：为系统长期运行打基础。  
可见性：中。  
复杂度：中。  
是否可 mock：是。  
是否适合第一切片：不建议，因为它是配置型功能，不能直接证明用户能完成任务交付。

### 推荐结果

第一切片选 A：任务创建闭环。

理由很简单：它是 AI 员工系统的入口动作。没有任务创建，就没有审批、执行、复盘。它用户可见、容易 mock、验收清楚、后续能自然接审批切片。

## 5.4 主案例第二轮：把第一切片收紧

确定候选闭环后，还要继续收紧。否则 coding agent 仍然可能扩展。

### 第一版切片描述：仍然有点大

```text
实现 AI 员工任务创建功能，用户可以创建任务，AI 员工理解任务并开始执行。
```

问题：

- “AI 员工理解任务”不够可验收。
- “开始执行”会引入真实 agent、工具调用和任务队列。
- 没有说明是否需要数据库。
- 没有说明页面范围。

### 第二版切片描述：更清楚

```text
实现任务创建第一切片：用户输入任务描述，系统生成一个可编辑的任务草案；用户确认后，任务进入任务列表，初始状态为“待执行”。本切片使用 mock 草案生成和前端本地状态，不接真实 agent，不接真实后端，不做审批和执行。
```

这一版明显更可施工，因为它写清了：

- 起点：用户输入任务描述。
- 过程：生成可编辑任务草案。
- 终点：进入任务列表，状态为待执行。
- 数据策略：mock 草案生成，本地状态。
- 不做：真实 agent、后端、审批、执行。

这就是可以交给 coding agent 的第一切片定义。

## 5.5 三组错误问法 vs 正确问法

### 组 1：从完整系统开始

错误问法：

```text
我要做一个 AI 员工系统，请直接帮我规划完整功能和开发步骤。
```

问题：GPT 会自动扩展角色、记忆、工具、调度、权限、日志、部署等内容。材料会变多，但你很难判断第一步到底该做什么。

正确问法：

```text
我想做一个 AI 员工系统。请不要展开完整功能。请只帮我识别 3 个候选最小闭环，每个闭环写清起点、终点、用户价值、复杂度和是否适合第一切片。
```

### 组 2：切片边界不清

错误问法：

```text
先做任务创建功能。
```

问题：“任务创建”可能包含自然语言理解、任务拆解、员工分配、入库、执行触发、通知等一堆内容。

正确问法：

```text
请只做任务创建第一切片：输入任务 → 生成可编辑草案 → 用户确认 → 进入任务列表。不要实现员工分配、真实执行、审批、通知、长期记忆。
```

### 组 3：没有验收导向

错误问法：

```text
帮我把这个功能做得好用一点。
```

问题：“好用”对 coding agent 不够明确。

正确问法：

```text
请把第一切片改写成可验收标准。每条标准必须能通过手工点击检查，格式为：操作步骤、期望结果、通过条件。
```

## 5.6 字段解释：最小闭环识别表

下面不是单纯给模板，而是解释每个字段为什么存在。

### 项目名称

帮助你把本次分析限定在一个项目里。不要在同一张表里混入多个项目。

### 完整想法

允许你先把大想法写完整。很多人一开始就强迫自己收敛，反而写不出来。正确做法是先放开，再收紧。

### 候选闭环

至少写 3 个。只写 1 个很容易陷入自己的第一反应。

### 起点

必须是用户动作，而不是系统内部动作。

### 终点

必须是用户能看见的结果。

### 用户价值

这一闭环解决用户什么问题。不要写技术价值。

### 复杂度

用低 / 中 / 高即可，不要一开始做复杂估算。

### 可否 mock

如果不能 mock，第一切片风险通常更高。

### 验收难度

问自己：非程序员能否通过页面点击检查？如果不能，说明还不够适合第一切片。

### 推荐闭环与理由

最后必须做选择。训练的关键不是列很多可能，而是形成决策。

```text
验收难度：低

候选闭环 3：执行结果闭环
起点：任务状态变为执行中
关键过程：系统生成执行结果，用户查看
终点：用户标记满意或要求返工
用户价值：看到 AI 员工的实际产出
复杂度：中高
可否 mock：部分可以
验收难度：中
主要风险：真实执行能力和结果质量不好控制

推荐第一闭环：任务创建闭环
推荐理由：它是系统入口，用户可见，能 mock，容易验收，后续可以接审批和执行。
暂不选择其他闭环的原因：审批依赖任务存在；执行结果依赖真实 agent 能力；员工配置不能直接验证任务交付体验。
```

## 5.9 第一切片拆解表：字段解释

### 第一切片名称

名称要短，最好能表达链路，不要只写“任务功能”。

推荐：

```text
任务创建 → 草案确认 → 入列表切片
```

### 一句话定义

用一句话说明这个切片从哪里到哪里。

### 页面范围

列出本切片涉及哪些页面或组件。页面范围越清楚，coding agent 越不容易顺手新增无关页面。

### 用户路径

按用户点击顺序写，不要按技术模块写。

### 数据策略

说明用 mock、本地状态、浏览器缓存、还是后端接口。第一切片通常优先 mock 或本地状态。

### 做 / 不做

这是最关键的字段。不要只写做什么，一定要写不做什么。

### 验收标准

每条都要能手工测试。

## 5.11 主案例填写示例：第一切片拆解表

```text
第一切片名称：任务创建 → 草案确认 → 入列表切片
一句话定义：用户输入任务描述，系统生成可编辑草案，用户确认后任务进入列表并显示为待执行。
起点动作：用户在任务创建页输入任务描述并点击“生成草案”。
终点结果：任务出现在任务列表中，状态为“待执行”。
页面范围：任务创建页、草案确认区域、任务列表页。
用户路径：
1. 打开任务创建页。
2. 输入任务描述。
3. 点击生成草案。
4. 查看并编辑草案。
5. 点击确认创建。
6. 跳转或刷新任务列表。
7. 在列表中看到新任务。
数据策略：本切片使用前端本地状态和 mock 草案生成，不接真实后端。

本切片做：
1. 任务描述输入框。
2. 生成草案按钮。
3. 草案卡片展示。
4. 草案字段可编辑。
5. 确认创建任务。
6. 新任务进入列表。
7. 状态显示为“待执行”。

本切片不做：
1. 不接真实 agent。
2. 不调用外部工具。
3. 不做真实任务执行。
4. 不做高风险审批。
5. 不做多员工调度。
6. 不做长期记忆。
7. 不做数据库持久化。

验收标准：
1. 空输入时不能生成草案。
2. 输入任务后点击生成草案，页面出现草案卡片。
3. 草案标题、目标、产出、风险等级可编辑。
4. 点击确认创建后，任务进入列表。
5. 列表中显示任务标题和状态“待执行”。
6. 页面中不出现员工配置、审批、执行结果等本版不做内容。

待确认项：
1. 草案字段是否只包含标题、目标、产出、风险等级？
2. 确认后是跳转到列表页，还是在当前页下方展示列表？
3. 本地状态是否需要刷新后保留？第一版建议不要求。
```

## 5.12 读者常见卡点

### 卡点 1：总觉得第一切片太简单，不像产品

很多人会担心：只做任务创建，会不会太简陋？

你要记住，第一切片的目的不是证明系统已经完整，而是证明方向没有偏。第一切片像修路时打通第一段通道。它不代表高速公路建完了，但它能证明路线是对的。

### 卡点 2：忍不住把审批也放进第一切片

审批很重要，但它依赖任务已经存在。如果你把任务创建和审批同时放进第一切片，问题会变多：到底是任务创建不好，还是审批规则不好？到底是状态设计不好，还是按钮位置不好？

第一轮先让任务能稳定进入列表。第二轮再做审批。

### 卡点 3：分不清“可 mock”和“假功能”

mock 不是假装完成产品，而是用低成本方式验证流程。

如果你明确写出“本切片使用 mock 草案生成，不验证真实 agent 能力”，它就是合理的开发策略。问题不在于 mock，而在于没有说明 mock 的边界，导致自己以为已经实现真实能力。

### 卡点 4：不知道怎么判断终点

终点最好满足三个条件：

1. 用户能看到。
2. 可以截图。
3. 可以写成验收项。

如果一个终点不能截图，通常说明它太偏系统内部。

## 5.16 本章小结补强

本章真正要训练的不是“会不会拆任务”，而是你能不能在 AI 很会扩展、很会补全、很会生成大文档的情况下，把它拉回一条短链路。

判断第一切片时，记住这句话：

```text
优先选择用户看得见、能 mock、能手工验收、能自然接下一步的闭环。
```

只要你能做到这一点，AI 协同开发就从“听模型发挥”变成了“由你控制节奏”。
