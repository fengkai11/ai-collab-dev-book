# 第 2 章：什么是切片式开发，为什么它比“大而全设计”更适合新手

> 版本：v0.1 全章初稿  
> 本章定位：基础训练章节

## 本章你要学会什么

你要理解切片不是把大任务拆小，而是拆出一段能跑通的业务闭环。一个好切片必须能看、能跑、能验收。

## 为什么这一章重要

AI 协同开发最容易失败的地方，往往不是模型不会写代码，而是人没有把目标、边界、检查点和验收方式定义清楚。本章的作用，是把一个容易凭感觉推进的环节，变成可以重复执行的训练动作。你不需要一开始掌握传统软件工程的全部知识，但你必须能把 AI 的输出限制在自己能审查、能判断、能返工的范围内。

## 核心概念

- 切片式开发：围绕可验证闭环推进。
- 纵向切片：从用户动作切到可见结果。
- 横向拆分：按前端、后端、数据库等层拆。
- 最小闭环：最短但完整的业务链路。
- 可预览、可运行、可验收。

## 核心观点

1. 切片不是小任务，而是小闭环。
2. 新手优先做纵向切片，不要横向铺满模块。
3. 好切片必须有用户动作和可见结果。
4. 切片越小，反馈越快，偏航越容易修。
5. 切片式开发不是降低目标，而是降低失控风险。

## 主案例推进

AI 员工系统可拆为任务创建、审批、执行结果、员工配置等候选切片。第一切片优先选“任务创建 → 草案确认 → 进入列表”，因为它最靠近用户第一动作，最容易预览和验收。

## 错误示范

```text
第一周做所有页面，第二周做所有接口，第三周做数据库，第四周联调。
```

这属于横向拆分。每层都有进度，但没有一条用户链路能完整跑通。

## 正确示范

```text
第一切片：用户输入任务 → 生成草案 → 用户确认 → 任务进入列表。
本切片不做真实执行、审批、长期记忆、多员工、复杂权限。
```

这是一条纵向切片，虽然小，但能验证核心入口。

## 方法拆解

### 1. 找用户动作

好切片通常从用户动作开始，例如输入任务、上传文件、选择商品。

### 2. 找可见终点

终点应该是用户看得见的结果，例如任务进入列表、客户清单生成。

### 3. 用 mock 降低复杂度

真实 AI、真实后端、真实数据源都可以先 mock，先验证流程。

### 4. 写不做项

不写不做项，AI 会默认可以扩展。

## 和 GPT 的对话演示

```text
请从下面 4 个候选切片中选择最适合作为第一切片的一个：任务创建、审批、执行结果、员工配置。
判断标准：用户可见价值、复杂度、是否容易预览、是否容易验收。
```

## 本章小结

切片式开发的核心是先跑通一条最小业务链路。它让新手把 AI 输出控制在可审查范围内。

## 补充说明：为什么纵向切片更适合 AI 协同开发

在传统团队里，横向拆分之所以可行，是因为团队中有人能统一把控架构，有人负责接口约定，有人负责联调，有人负责测试。但新手和 AI 协同开发时，通常没有这么多角色。你一个人既要提需求，又要审页面，又要让 coding agent 改代码，还要验收结果。

这种情况下，横向拆分会把风险推迟到最后。前端做完时，你不知道后端能不能接；接口做完时，你不知道页面是否真的需要；数据库做完时，你不知道业务流程是否已经变了。

纵向切片的好处是，每一次都围绕用户价值走一小段。你不需要判断全系统，只需要判断这一段是否成立。

## 切片大小的判断标准

一个切片太大，通常有这些信号：

- 描述里出现“完整”“全部”“所有”；
- 需要同时接多个外部系统；
- 需要复杂权限、长期记忆、任务队列、消息通知一起完成；
- 验收项写不出来；
- 页面预览超过 5 个核心页面；
- 你解释给别人听需要超过 2 分钟。

一个切片太小，也可能有问题：

- 只有一个按钮，没有结果；
- 只有数据库表，没有用户动作；
- 只有页面静态布局，没有状态变化；
- 做完后无法判断业务是否成立。

好的第一切片通常介于两者之间：功能不多，但链路完整。

## 主案例切片序列建议

AI 员工任务系统可以按下面序列推进：

```text
切片 1：任务创建与草案确认
切片 2：高风险任务审批
切片 3：任务执行结果展示
切片 4：任务返工与满意度反馈
切片 5：AI 员工基础配置
切片 6：任务复盘和经验沉淀
```

注意这里没有一开始做员工配置。原因是配置需要真实任务来验证，否则你不知道哪些配置是真需求，哪些只是看起来专业。

## 切片命名规则

好的切片名称最好包含动作和结果：

- 好：创建任务并进入列表；
- 差：任务模块；
- 好：生成候选客户并标记跟进；
- 差：客户管理；
- 好：上传试卷并生成错题清单；
- 差：学习系统。

名称越具体，越不容易发散。

# v0.3 扩写：切片不是拆任务，而是拆闭环

很多新手第一次听到“切片式开发”，会自然理解成“把大任务拆小”。这个理解只对了一半。真正重要的不是“小”，而是“闭环”。

一个任务可以很小，但不是好切片。例如：

```text
先建数据库表。
```

这确实很小，但用户看不见，也无法单独验证业务价值。它只是一个横向技术任务。

一个切片也可以包含前端、状态、mock 数据、简单交互，看起来涉及多个层面，但只要它围绕一条用户路径形成闭环，它就是好切片。例如：

```text
用户输入任务 → 系统生成草案 → 用户确认 → 任务进入列表。
```

它可能需要页面、按钮、状态、列表渲染，但用户能走完，产品能验收，后续能接真实后端。这就是纵向切片。

## 2.1 横向拆分为什么容易坑新手

传统技术拆分经常按层划分：前端页面、后端接口、数据库、权限、测试、部署。这种拆法对成熟团队很自然，因为团队里有人分别负责不同层，并且有架构师保证整体一致。但新手用 AI 协同开发时，按层拆分会遇到三个问题。

### 问题一：每一层都做了一点，但没有功能能用

如果第一周做完数据库，第二周做完接口，第三周做完页面，第四周才联调，你要等很久才知道需求有没有错。AI 开发的优势是反馈快。如果你用横向拆分把反馈推迟，就浪费了 AI 的最大优势。

### 问题二：你无法审查中间产物

数据库表是否设计合理？接口是否 RESTful？状态管理是否优雅？这些问题对新手不友好。你可能只能觉得“看起来专业”。但页面路径、按钮文案、列表状态、错误提示，你能审查。切片式开发就是优先制造你能审查的产物。

### 问题三：早期技术决策会锁死错误方向

当用户路径还没确认时，提前设计复杂后端，会让后续修改变重。你可能只是想把“处理中”改成“待执行”，但因为状态机、接口、数据库都已经铺开，改动变得复杂。

## 2.2 什么是纵向切片

纵向切片不是只做前端，也不是只做假数据。它的核心是：**沿着一条用户路径，从入口到结果，做出一个可运行、可观察、可验收的小版本。**

一个好纵向切片通常包含：

1. 用户入口：用户从哪里开始；
2. 核心动作：用户做什么；
3. 系统反馈：系统给出什么响应；
4. 状态变化：数据或页面如何变化；
5. 终点结果：用户看到什么结果；
6. 验收标准：如何判断成功。

以主案例为例：

| 元素 | 内容 |
|---|---|
| 用户入口 | 任务创建页 |
| 核心动作 | 输入任务描述，点击生成草案 |
| 系统反馈 | 显示任务草案 |
| 状态变化 | 用户确认后，任务加入列表 |
| 终点结果 | 列表出现一条“待执行”任务 |
| 验收标准 | 空输入不能提交，草案可编辑，确认后列表更新 |

这就是第一切片的骨架。

## 2.3 一个好切片的 6 个判断标准

### 标准一：能看见

用户或产品负责人能在页面上看到结果。如果一个切片做完后只能在代码里看变化，对新手就不友好。

### 标准二：能操作

用户能执行动作，不是只看静态页面。至少要能输入、点击、确认、取消、查看状态。

### 标准三：能验收

必须能写出通过/不通过的验收项。例如“输入为空时，生成草案按钮不可点击”。这比“交互要友好”更可验收。

### 标准四：边界清楚

切片必须写明“不做什么”。例如第一切片不做真实 agent 执行、不做长期记忆、不做多员工调度。

### 标准五：能接下一片

第一切片做完后，应该自然接第二切片。任务创建闭环之后，可以接审批切片；审批之后，可以接执行结果切片。

### 标准六：风险可控

如果做错了，能小范围返工，而不是推倒整个系统。

## 2.4 主案例：为什么不先做“员工配置”

很多人会觉得，既然是 AI 员工系统，第一步应该先设置 AI 员工：员工名称、职责、工具权限、记忆范围、风险等级、工作时间、汇报方式。这些都合理，但不适合作为第一切片。

原因有三点：

1. **用户价值不直接。**配置员工是为了让员工执行任务。如果任务创建闭环还没跑通，配置员工的价值无法验证。
2. **字段会无限膨胀。**一旦开始做员工配置，AI 很容易扩展出权限、角色、技能、知识库、工具市场、审批策略。
3. **验收难度高。**“员工职责配置是否合理”很难在第一版验收。但“任务能否创建并进入列表”很容易验收。

因此，第一切片选择任务创建，而不是员工配置。

## 2.5 候选切片打分示例

| 候选切片 | 用户可见性 | 验收难度 | 实现复杂度 | 后续承接 | 是否适合第一片 |
|---|---:|---:|---:|---:|---|
| 任务创建 → 草案确认 → 入列表 | 高 | 低 | 低 | 高 | 适合 |
| 高风险审批 | 中 | 中 | 中 | 高 | 第二片更合适 |
| 执行结果展示 | 中 | 中 | 中 | 中 | 等任务存在后再做 |
| 员工配置 | 中 | 高 | 高 | 中 | 不适合作为第一片 |
| 长期记忆 | 低 | 高 | 高 | 中 | 暂不做 |

这个表不是为了追求数学精确，而是帮助你把“感觉”变成讨论依据。

## 2.6 切片候选清单模板扩写

### 字段解释

- 候选切片名称：用一句短语命名；
- 起点动作：用户第一步做什么；
- 终点结果：用户最后看到什么；
- 用户可见价值：为什么用户会觉得有用；
- 本片做什么：明确范围；
- 本片不做什么：防止扩张；
- 主要风险：可能卡在哪里；
- 验收方式：如何判断做完。

```markdown
- 本片做什么：
- 本片不做什么：
- 主要风险：
- 验收方式：

## 候选切片 2

```

### 主案例填充

```markdown
## 候选切片 1
- 名称：任务创建与草案确认
- 起点动作：用户输入任务描述
- 终点结果：任务进入列表，状态为“待执行”
- 用户可见价值：用户第一次感受到可以把任务交给 AI 员工
- 本片做什么：任务输入、草案生成、草案编辑、确认入列表
- 本片不做什么：真实执行、审批、权限、长期记忆
- 主要风险：草案内容不符合预期；状态文案不清楚
- 验收方式：按创建流程逐步测试
```

## 2.7 练习扩展：把横向任务改成纵向切片

题目：

```text
第 1 周做所有页面；第 2 周做所有接口；第 3 周做数据库；第 4 周接 AI；第 5 周测试。
```

参考答案：

```text
切片 1：任务创建闭环
用户输入任务 → 生成草案 → 编辑确认 → 进入任务列表。使用 mock 数据，不接真实后端。

切片 2：审批闭环
高风险任务 → 触发审批弹窗 → 用户同意/拒绝 → 任务状态更新。

切片 3：执行结果闭环
待执行任务 → 模拟执行 → 展示执行结果 → 用户确认满意/重新执行。
```

解释：这三个切片每个都能独立演示、验收和返工。它们不是按技术层拆，而是按用户价值链路拆。

## 2.8 卡住时怎么问 GPT

当你不知道怎么切时，可以这样问：

```text
我有一个产品想法：{写下你的想法}。
请不要展开完整系统。
请帮我列出 5 个候选纵向切片，每个切片必须包含：用户起点动作、系统反馈、终点结果、可验收标准。
然后按“用户可见价值、实现复杂度、验收难度、后续承接”给出推荐排序。
```

当你担心切得太大时，可以这样问：

```text
请审查下面这个切片是否过大。
如果过大，请拆成 2–3 个更小的纵向切片。
注意：每个切片都必须能看、能操作、能验收。
```

## 2.9 本章扩写小结

切片式开发的重点不是“少做”，而是“先做能验证方向的那一段”。你不是放弃完整系统，而是拒绝在没有验证入口闭环之前，把精力投入到庞大的架构和模块中。
